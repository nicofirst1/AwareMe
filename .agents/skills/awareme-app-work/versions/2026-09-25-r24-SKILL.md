# Working on AwareMe

Orientation first: `AGENTS.md` (map), `docs/spec.md` (the contract; §5.1 content rules, §13 hard constraints), `docs/DECISIONS.md` (standing decisions). This skill covers HOW to work and verify here; those files cover WHAT is true.

## Setup

- Work in your assigned worktree. Provision per `docs/DECISIONS.md`: `npm install --legacy-peer-deps`, then the expo-asset remedy.
- Gates: `npm run typecheck`, `npx jest`, `npm run lint`. Compare like-for-like — your worktree's node_modules (not main's), same command, same location — and a baseline failure counts as current only when re-run at this HEAD; otherwise cite it as cited. Baselines live in the round hub.
- Jest discovery: integration tree `npx jest --testPathIgnorePatterns=/\.worktrees/` (`--watchPathIgnorePatterns` is watch-mode only, excludes nothing); inside a worktree plain `npx jest` (that pattern would exclude the worktree root itself: false zero).
- Corpus resolution: a fresh worktree resolves the committed example seed — the gitignored owner overlay (`stems.content.ts`) is absent there. Before the first capture or any content-derived receipt from a fresh worktree, copy the owner overlay in byte-identical (never staged) and bank a content-parity probe: the on-screen discriminator the receipted baseline predicts (Home "N stems ready"); a mismatch means rebuild before anything is banked. Receipts and pins name which corpus resolved (owner vs example).

## Device work with pi-droid

Load the pi-droid skills for the tool sets: `android-screen` (perception), `android-interact` (input), `android-automate` (waits, find-and-tap, scroll-until-found). Check `android-plugin` for capabilities before hand-rolling them. A round with multiple emulators adds the pool rules: `parallel-device-pools.md`.

**Lock first.** Post a `LOCK-CLAIM: <device>-lock` hub line before ANY adb interaction, including emulator boot, kill, and reboot-recovery — recovering a frozen emulator is device work, not an exemption. Claims posted as NOTE lines (or not posted) are protocol breaches. After appending a claim, re-read for competing claims immediately: reach far enough above the claim to cover them, or grep the claim class across the whole file (a bounded line-range sample can miss a claim just above the window); if a competing claim sits earlier in the file, the earlier claim wins (the hub is append-only; file order is authoritative when pane clocks drift), and the later claimant yields and re-queues. Release a lock only after completing all captures and preserving app state: a reinstall or `adb emu kill` without release destroys the holder's work.

**Observe, then tap.** Tap by text/id/element index from annotated screenshots, via pi-droid tools. The screen is the source of truth, not your last dump: after every screen change take a fresh dump/screenshot before the next tap. Inverted, offscreen, or invalid bounds mean a stale observation — re-observe, never tap old coordinates. Presence, absence, and reachability claims come from a settled screen — byte-identical re-dumps before trusting the node, and a dump carrying degenerate bounds (negative width or height, bottom above top) is discarded as evidence for any such claim. The endemic uiautomator quirk is negative computed dimensions with all-positive coordinates (a negative-coordinate grep finds none), so bounds scans match on dimensions, and a 'no invalid bounds' scan states the definition it used. A dump whose degenerate nodes are the capture-time quirk is disclosed as such. XML proves a node rendered, not that the user can see it: a visibility or above-the-fold claim needs a capture with pixel geometry (p7 w2t6: the footer line rendered in XML but sat below the fold). Prefer pi-droid tools for all taps; raw `adb shell input tap x y` is a fallback only when a pi-droid tool cannot express the step, and the fallback must be disclosed in the evidence trail.

**Pair hashes and names in ONE command.** `md5 -r` / `shasum` print `hash path`; `ls` output re-sorts lexically and mispairs (r15, 2026-09-22: a pasted-vs-`ls` pairing produced a false cross-bank collision that froze three cycles). Re-derive any diagnostic before steering conclusions on it; a diagnostic that fails re-derivation is retracted in the hub by an appended superseding line that names the exact quote it retires (never edit history), and agents frozen on a retracted record resume immediately. Within-bank identical dumps are the F27 staleness class: re-capture with a fresh dump and name from the dump's content.

**Shared-singleton events take a lock AND a FLAG.** `adb kill-server` (or any adb daemon restart) disconnects every concurrent adb user on the host: take the emulator lock and post a FLAG before running it, and prefer non-destructive recovery (`adb devices`, re-connect) over kill-server.

**Restore.** Stop the app, stop Metro, `adb reverse --remove-all`, verify port 8081 is free, and restore device config you changed (density, theme, locale) before releasing the lock. Restoration claims are verified commands, not intentions, and the LOCK-RELEASE line names its banked proof — a post-restore capture or XML dump under the cycle's evidence dir, not prose state description alone (p8 t1-audit f4: device left foreground, release row described state in prose).

## Verification methodology: vision-first, hypothesis-driven

The failure mode this skill exists to prevent: wandering around the app clicking randomly, then writing claims from memory.

1. **Hypothesis first.** From the ticket, write the expected behavior as a checkable statement before touching the device ("the DayField opens a weekday list with capitalized names").
2. **Targeted interaction.** Drive straight to the surface that tests the hypothesis. Take only taps/scrolls that answer a stated question.
3. **Capture.** Annotated screenshot + UI-tree dump for every claim. Pull a bounded logcat window around any crash/ANR or intent launch.
4. **Vision read.** The capture must be SEEN by a vision-capable reader before anything is claimed. If your session model renders images, read the capture yourself and describe what it actually shows (colors, layout, text) against the hypothesis. If it does not (text-only model: the read tool rejects image attachments), delegate the visual inspection to a vision-capable agent (the headless one-shot or native vision agent below) and record its description verbatim as the evidence. A claim backed only by "the flow worked" is not evidence. Absence claims obey the same rule: pixel probes sample points, so a clean probe cannot prove a visual defect is absent anywhere in the frame — a negative claim needs the vision reader over the full capture.
   - Vision reads run ONLY on iais-genai models — never openai, openrouter, or any non-Fraunhofer endpoint: app captures are owner-local content (r16, 2026-09-22, owner rule after two off-cluster probe reads were disclosed in the hub).
   - Headless one-shot from a bare pane: `pi -p --no-session -nt --model iais-genai/<model> @<image>` (`-nt` bypasses the agent-comms lock). The bridge accepts pi's native attachment format (r17, 2026-09-22: the earlier 400 "Unexpected message role" was rollout-transient, proven by request-capture replay and a live native probe). Curl fallback for outage diagnosis: POST <baseUrl>/chat/completions, single user message with content array [text, image_url data-URL], max_tokens ≥ 2000 for reasoning models — the answer must clear the reasoning channel.
   - Native vision agents: spawn a pi pane with the vision model (`herdr agent start <name> --kind pi --pane <P> -- --model iais-genai/<model>`) — it reads screenshots via its normal read tool, and with the android extension it can look at and drive the app directly for audits; emulator-lock discipline applies to any agent that touches a device.
   - Bank the read, not the claim: a delegated vision read's verbatim transcript is banked beside the capture set, recording the model name and the input capture's identity inside itself — the input named by filename AND its md5 beside it (transcript-input binding, p10: t4 carried md5 4/4, t3 8/9 filename-only, t2 0/10 and passed only through a reconstructed BINDING.md closure); a read surviving only as a receipt sentence rides an independent XML/capture corroboration. Every capture the set claims as vision-read carries its OWN banked transcript — a set with per-pair reads banked 8/9 is a gap, not a pattern (p8 t1-audit f1). A gap closed by fresh off-bank verification (a reviewer's or coordinator's own read, probe, or re-derivation) lands a clearly labeled artifact INTO the bank it closes before the verdict row — a closure that lives only in verdict prose leaves the bank permanently short (gap-closure read banking, axis registered 2026-09-24). A partial content pass names the frames it skipped, never just a count. A fallback or retry names which model produced each read and which endpoints were tried and failed (p7: iais-genai-only passes with 404s named, audit-praised).
5. **Classify.** Every claim in a report or comment states its evidence class: live observation, UI dump, capture file, or logcat, with the exact filename.
6. **Preserve.** Evidence lives under `.coordination/<round>-captures/` or the round's evidence dir: real files (a 0-byte stub is not evidence), identical captures are cited once, not as distinct observations, and every capture instruction names the exact tree root and directory (worktree `.captures/<id>/` vs repo root) plus the coordinator's backup path, so pointers never depend on guessing which tree the bank lives in.
7. **Capture-set integrity (device campaigns).** Verify a screen's identity from its UI dump BEFORE naming the capture file after it. After any theme or density change, capture a probe frame and hash it: the md5 must differ from the previous state's probe, or the change did not take effect. Before banking a capture set, post an md5 list across the whole set. Content-parity probes (the corpus discriminator) are BANKED ARTIFACTS — a capture or dump file with its md5 beside the set, never prose in a receipt alone (p8 t1-audit f2). A vision-reader content pass over the banked set is a merge gate, not a formality. Freeze the build for the whole capture window — no commit amends while captures are in flight; an unavoidable amend forces rebuild + reinstall + recapture of the affected frames, and release lines name the shipped head with the re-taken frames disclosed. A planned scene whose surface cannot exist in the build under test (a predecessor's surface merged after your base) is a named pending gap with its reason — never simulated, never blindly re-captured; review and audit accept or reject the gap by that stated reason. A device-found defect fixed in-commit banks its pre-fix measurement pair beside the post-fix pair (or the manifest labels the already-existing pre-fix files as that defect's evidence) — pre-fix files sitting unmanifested in the bank dir read as housekeeping residue, and the fix's justification is prose-only after teardown (pre-fix measurement banking, p10 t2). An artifact banked after its capture names the capture event beside its md5 (a device-side timestamp read, or the hub row that took it) — file mtime is the banking moment, not the capture time (capture-time vs bank-time provenance, p9 t1).

For color/layout claims: name the palette token from `src/constants/theme.ts` you expect, then verify the rendered pixels or the UI tree against it. Pixel-count scripts supplement visual inspection; they never replace it and never ground an absence claim (step 4).

## Copy rules

User-visible copy, issue text, reports, hub lines: curly apostrophes, no em dashes, plain words. Every copy pass adds the byte-level form check alongside the tone and content checks: straight apostrophes and em dashes in user-visible strings fail. Commit only original example content (spec §5.1).

## Mockup-first rule (ADR-0008, standing)

Every design change ships an HTML mockup first, and the owner's agreement on the mockup gates any application code. Visual changes: the design.md + HTML mockup pipeline (device-accurate sizes, example data, §5.1 discipline). Logic changes with a visual surface: an HTML mirror page running the real pure functions 1:1 over example data; the owner tries it in the browser; the agreed logic ports back into the one module + tests. Mockups/mirrors live in `.coordination/<round>-design/`.

## Round protocol (delegated cycles)

The round hub (`.coordination/<round>.md`) is the durable record: timestamped one-line transitions, append-only. Blockers are FLAG lines, never notes. Heartbeat every ~30 min of work. Duration claims (elapsed, budget, lateness) are read from the shell clock (`date`) at post time, never estimated. Check the line count after every append (`wc -l` before and after). The coordinator side (amendment snapshots, hub backup, merge gates, PLAN.md lifecycle) lives in `round-ops.md`.

A cycle's first hub interaction is the STARTED row, posted before reading work begins — it is the one row whose absence nothing later in the trail recovers.

Researcher leg (map-before-implementer). A cycle touching shared surfaces (repository, write flow, settings, session engine) or high blast radius opens with a read-only researcher leg: no edits, commits, or device use; one report file under `.coordination/reports/`; a bounded ~20-minute cap (a map at 80% beats no map); every claim re-grepped at the pinned base with file:line, never copied from stale audits. A completeness claim ("zero callers", "all consumers") carries the exact grep command beside it and sweeps the full tsconfig-included tree (src/, scripts/, export suites), never a directory guess; a sketch that edits a predicate quotes the predicate's exact current shape. Out-of-map necessities are named in the map so the charter pre-declares grants. A map written after a predecessor cycle merged consumes the landed facts from the merged tree (tag in-flight engine seams for re-verification at the implementer's own base) and lists already-shipped surfaces as assert-don't-touch — verify the landed behavior is present and pinned, never re-edit the other cycle's file. DONE with the report path wakes the coordinator.

Excursion discipline. Out-of-map needs run in two tiers: anticipated necessities are pre-declared in the charter as scoped grants (exact surface, one-line rationale); an emergent out-of-map need is a pre-edit FLAG naming the exact lines, the recipe, and why — in-map work continues while it waits. Consume grants exactly as scoped and disclose the consumption in the receipts.

Cycle shape: impl agent → READY → reviewer (outcome: spec fit + gates) → review loop settles (verdict in, requested changes verified) → methodology auditor LAST, analyzing the complete trail: implementation, review findings, and how the implementer handled them. The auditor does NOT run in parallel with the reviewer — an audit that closes before the review loop ends cannot judge the review exchange (did the reviewer verify independently, did the implementer respond to findings or argue them away) or the trail the loop produced. Both fresh-context on the code; both must approve. The owner-present default gates the merge on both approvals, auditor LAST. Unattended rounds under standing owner authorization run the post-merge variant: merge on the reviewer's APPROVAL, the methodology audit landing after the merge as the process post-mortem — its scope is unchanged, the complete trail (packet 3 ran the variant 11/11 with clean audits, 2026-09-22). If the reviewer requests changes, the auditor waits for the re-verified fix, and its charter covers the full loop.

READY means the implementation is done and the evidence is either complete OR the pending part is device work blocked by the emulator queue: in that case the READY line lists the pending captures explicitly, the reviewer spawns immediately, the methodology auditor still waits for the review loop to settle (LAST), and the merge additionally gates on the capture set landing (or the reviewer explicitly accepting the partial evidence). A READY line carries its own identity: worktree + branch + HEAD, gate numbers vs the named baseline (or the baseline cited as not re-run), one evidence-class sentence with filenames, and the build state — dirty working-tree edits are a build input, so record the `git status --porcelain` count beside HEAD plus a working-tree fingerprint (`git diff HEAD | shasum -a 256`; tracked staged+unstaged edits only, not exact artifact identity; counts/hashes, never private content). The row announcing a capture build carries the same fingerprint of the tree being built, taken before the build runs — a fingerprint whose first appearance is the post-commit READY leaves the pre-commit build window unreconstructable (build-time tree binding, fired 0-for-3 in p10: t4's founding case, t3 one cycle later, t2 with no build-announcing row at all). Install time and an APK newer than the commit are not build identity. A READY posted alongside an open FLAG names the scope it covers, and the coordinator resolves the FLAG before spawning review (or records the review as in-map-only) — a FLAG and a READY posted in the same minute race each other (t8, 2026-09-22). After READY, STOP: no further hub lines, captures, or edits until the reviewer's verdict — post-READY work races the reviewer, and READY is the implementer's final row (no DONE follow-up; the verdict and the merge carry the cycle from there).

The READY gate standard: 0 failed like-for-like in the worktree; baseline failures are named and cited, ticket-mandated failures are fixed before READY, and assertions that cannot be derived from the seed module's shape go back through FLAG. Worktree gates resolve one corpus (the example seed — the gitignored owner overlay is absent), so test expectations derive from structure the test creates (fixtures, inserts, named constants), never from corpus shape or corpus-indexed constants; a corpus-derived expectation is signed off only by the owner-corpus gate at main (p7 w2t2, 2026-09-23: green in the worktree, Expected 5 / Received 29 at main, engine correct).

Receipts quote committed state: every receipt (gate numbers, line positions, test counts) names the tree it was taken from — the commit or "at HEAD" — never a session-live position a later edit moves (packet 3, 2026-09-22: receipt slips recurred across three cycles, one escaping review entirely, and they recurred after the matching audit axis was registered — rules live here, not only in the registry). Headline counts (file counts, diff lines, red/green ratios) come from a fresh run at post time (`git diff --numstat <base>..<HEAD>`), never hand-summed or carried from an earlier compose. A sentence asserting what code WOULD do under a hypothetical edit carries its verification class — "live-run verified" with the recipe, or "reasoned, unverified". A check claim names the scan's actual scope — which files, screens, or labels the grep or regex covered, never more than it ran. The pre-review self-audit's old-shape grep sweeps comments and docblocks too — a comment still describing a retired mechanism is a finding, not a note for the next cycle (p7 w2t2: the stale programRead.ts docblock was caught by review, not self-audit). In a coordinator-provisioned worktree the expected `git status --porcelain` baseline is one line (the node_modules symlink); state it as that, never a bare 0. A reviewer re-derivation lands its recipe beside the number: the base commit, the files copied, the command run — the verdict's numbers then carry a durable evidence layer, not prose alone.

The methodology auditor judges HOW the work was done — hypothesis discipline, capture quality, vision use, protocol compliance, ownership compliance — never whether the code is correct. Each auditor's verdict MUST end with one proposed audit axis for the next audits: the common failure case it believes the current axes would miss, stated as `Proposed axis: <name> — catches: <failure case>`; the coordinator folds accepted axes into future auditor charters, so each audit makes the next one sharper. Axes live with scores in `.agents/skills/methodology-auditor/axis_classification.md` (active set = top 5 by score).

Methodology findings that reveal a skill gap: post an `AUDIT-FINDING` hub line stating the gap and the proposed amendment. Agents never edit this skill mid-round; the coordinator verifies, consolidates, and folds accepted findings in (mechanics in `round-ops.md`). On a `SKILL-UPDATE` hub line, re-read the skill file before your next device interaction or claim; audits judge against the amended text.

Full-app visual audits use the vision audit swarm: `vision-audit-swarm.md`.
