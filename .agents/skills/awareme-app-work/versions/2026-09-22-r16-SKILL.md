# Working on AwareMe

Orientation first: `AGENTS.md` (map), `spec.md` (the contract; §5.1 content rules, §13 hard constraints), `DECISIONS.md` (standing decisions). This skill covers HOW to work and verify here; those files cover WHAT is true.

## Setup

- Work in your assigned worktree; provision with `npm install --legacy-peer-deps --no-audit --no-fund`, then the expo-asset remedy from `DECISIONS.md` (`npm install expo-asset@57.0.16 --no-save`).
- Gates: `npm run typecheck`, `npx jest`, `npm run lint`. Baselines live in the round hub; compare like-for-like — your worktree's node_modules (not main's), same command, same location. Jest discovery: integration tree `npx jest --testPathIgnorePatterns=/\.worktrees/` (`--watchPathIgnorePatterns` is watch-mode only, excludes nothing); inside a worktree plain `npx jest` (that pattern would exclude the worktree root itself: false zero). A baseline failure counts as current only when re-run at this HEAD; otherwise cite it as cited.
- Emulator: `./scripts/emulator.sh` (bounded boot wait). APK: `./scripts/rebuild-android.sh`.

## Emulator work with pi-droid

Load the pi-droid skills for the tool sets: `android-screen` (perception), `android-interact` (input), `android-automate` (waits, find-and-tap, scroll-until-found). Check `android-plugin` for capabilities before hand-rolling them.

- Device pools (parallel rounds): multiple emulators may run side by side, each a separate lockable resource. Boot clones on explicit ports (`emulator -avd <name> -port 5556 -no-snapshot -no-boot-anim -no-window -gpu swiftshader_indirect &`; serial = `emulator-<port>`). Target YOUR device only, and PROVE the targeting at cycle start: `ANDROID_SERIAL` env alone is NOT sufficient (r15, 2026-09-22: panes with `--env ANDROID_SERIAL` still ran on the wrong device until each explicitly registered) — the ground truth is each pane's pi-droid registration, so every parallel cycle posts its targeting proof in its first hub NOTE (the `android_devices` list output plus the `-s <serial>` scopes of its recent device calls), and the coordinator cross-checks serials against the lock map before captures count. Scope `adb install`/`emu kill`/`reverse`/`kill-server` with `-s <serial>` when multiple devices are attached. Locks are PER DEVICE: `LOCK-CLAIM: emulator-5556-lock` (earliest-in-file wins, same discipline), and 5554-class shared devices may be designated read-only-reserved by the coordinator. RAM guardrail: before booting another emulator require free+inactive ≥ 4 GB AND swap free ≥ 1.5 GB AND fewer than 3 running emulators; prefer release-APK installs (no Metro) for parallel work; `pm clear` the app between occupants of a pooled device, or use ephemeral clones for hard isolation. Restore device config you changed (density, theme, locale) before releasing.
- Diagnostics that pair hashes with names pair them in ONE command (`md5 -r` / `shasum` print `hash path`); never paste md5 output against `ls` — `ls` re-sorts lexically and mispairs (r15, 2026-09-22: this produced a false cross-bank collision that froze three cycles). Re-derive any diagnostic before steering conclusions on it; a diagnostic that fails re-derivation is retracted in the hub by an appended superseding line (never edit history), and agents frozen on a retracted record resume immediately. Within-bank identical dumps are the F27 staleness class: re-capture with a fresh dump and name from the dump's content.
- Lock discipline: post a LOCK-CLAIM line before ANY adb interaction, including emulator boot, kill, and reboot-recovery - recovering a frozen emulator is device work, not an exemption. Claims posted as NOTE lines (or not posted) are protocol breaches. After appending a claim, re-read the hub tail immediately: if a competing claim sits earlier in the file, the earlier claim wins (the hub is append-only; file order is authoritative when pane clocks drift). A later claimant yields and re-queues. Release a lock only after completing all captures and preserving app state; a reinstall or `adb emu kill` without release destroys the holder's work.
- Tap by text/id/element index from annotated screenshots, via pi-droid tools. The screen is the source of truth, not your last dump: after every screen change take a fresh dump/screenshot before the next tap; inverted, offscreen, or invalid bounds mean a stale observation — re-observe, never tap old coordinates. Prefer pi-droid tools for all taps; raw `adb shell input tap x y` is a fallback only when a pi-droid tool cannot express the step, and the fallback must be disclosed in the evidence trail. `adb kill-server` (or any adb daemon restart) is a shared-singleton, lock-relevant event: it disconnects every concurrent adb user on the host. Take the emulator lock AND post a FLAG before running it; prefer non-destructive recovery (`adb devices`, re-connect) over kill-server.
- Restore device state after work: stop the app, stop Metro, `adb reverse --remove-all`, verify port 8081 is free. Claims of restoration must be verified commands, not intentions.

## Verification methodology: vision-first, hypothesis-driven

The failure mode this skill exists to prevent: wandering around the app clicking randomly, then writing claims from memory.

1. **Hypothesis first.** From the ticket, write the expected behavior as a checkable statement before touching the device ("the DayField opens a weekday list with capitalized names").
2. **Targeted interaction.** Drive straight to the surface that tests the hypothesis. Take only taps/scrolls that answer a stated question.
3. **Capture.** Annotated screenshot + UI-tree dump for every claim. Pull a bounded logcat window around any crash/ANR or intent launch.
4. **Look at it.** The capture must be SEEN by a vision-capable reader before anything is claimed. If your own session model renders images, read the capture yourself and describe what it actually shows (colors, layout, text) against the hypothesis. If it does not (text-only model: the read tool rejects image attachments), delegate the visual inspection to a vision-capable agent (registry agent "eyes" or equivalent) and record its description verbatim as the evidence. A claim backed only by "the flow worked" is not evidence. Absence claims obey the same rule: pixel probes sample points, so a clean probe cannot prove a visual defect is absent anywhere in the frame — a negative claim needs the vision reader over the full capture.
5. **Classify.** Every claim in a report or comment states its evidence class: live observation, UI dump, capture file, or logcat, with the exact filename.
6. **Preserve.** Evidence lives under `.coordination/<round>-captures/` or the round's evidence dir: real files, no 0-byte stubs, no duplicate files cited as distinct observations. If two captures are identical, say so and cite one.
7. **Capture-set integrity (device campaigns).** Verify a screen's identity from its UI dump BEFORE naming the capture file after it. After any theme or density change, capture a probe frame and hash it: the md5 must differ from the previous state's probe, or the change did not take effect. Before banking a capture set, post an md5 list across the whole set. A vision-reader content pass over the banked set is a merge gate, not a formality.

For color/layout claims: name the palette token from `src/constants/theme.ts` you expect, then verify the rendered pixels or the UI tree against it. Pixel-count scripts supplement visual inspection; they never replace it and never ground an absence claim (see step 4).

## Round protocol (delegated cycles)

The round hub (`.coordination/<round>.md`) is the durable record: timestamped one-line transitions, append-only. Blockers are FLAG lines, never notes. Heartbeat every ~30 min of work. Duration claims (elapsed, budget, lateness) are read from the shell clock (`date`) at post time, never estimated.

Cycle shape: impl agent → READY → reviewer (outcome: spec fit + gates) → review loop settles (verdict in, requested changes verified) → methodology auditor LAST, analyzing the complete trail: implementation, review findings, and how the implementer handled them. The auditor does NOT run in parallel with the reviewer — an audit that closes before the review loop ends cannot judge the review exchange (did the reviewer verify independently, did the implementer respond to findings or argue them away) or the trail the loop produced. Both fresh-context on the code; both must approve → merge. Sequencing exceptions: none by default; if the reviewer requests changes, the auditor waits for the re-verified fix, and its charter covers the full loop. READY means the implementation is done and the evidence is either complete OR the pending part is device work blocked by the emulator queue: in that case the READY line lists the pending captures explicitly, the reviewer spawns immediately, the methodology auditor still waits for the review loop to settle (LAST), and the merge additionally gates on the capture set landing (or the reviewer explicitly accepting the partial evidence). A READY line carries its own identity: worktree + branch + HEAD, gate numbers vs the named baseline (or the baseline cited as not re-run), one evidence-class sentence with filenames, and the build state — dirty working-tree edits are a build input, so record the `git status --porcelain` count beside HEAD plus a working-tree fingerprint (`git diff HEAD | shasum -a 256`; tracked staged+unstaged edits only, not exact artifact identity; counts/hashes, never private content). Install time and an APK newer than the commit are not build identity. After READY, STOP: no further hub lines, captures, or edits until the reviewer's verdict — post-READY work races the reviewer. The methodology auditor judges HOW the work was done — hypothesis discipline, capture quality, vision use, protocol compliance, ownership compliance — never whether the code is correct. Each auditor's verdict MUST end with one proposed audit axis for the next audits: the common failure case it believes the current axes would miss, stated as `Proposed axis: <name> — catches: <failure case>`; the coordinator folds accepted axes into future auditor charters, so each audit makes the next one sharper. Axes live with scores in `.agents/skills/methodology-auditor/axis_classification.md` (active set = top 5 by score; auditors propose and score, the coordinator prunes). Methodology findings that reveal a skill gap go to the coordinator: auditors and impl agents never edit this skill mid-round; they post an `AUDIT-FINDING` hub line stating the gap and the proposed amendment, and the coordinator verifies, consolidates, and folds accepted findings in under the amendment discipline below. When the coordinator amends this skill, it posts a `SKILL-UPDATE` hub line and steers every working agent to re-read it; agents re-read the file on such a line before their next device interaction or claim, and audits judge against the amended text. Amendment discipline: every amendment is numbered (counted in the round hub); BEFORE applying one, the coordinator snapshots the current SKILL.md into `versions/<date>-r<N>-SKILL.md` in this skill's directory, and at every 3rd amendment reviews the axis registry (prune if more than 5 axes: drop the lowest score, oldest wins ties, sort the rest by score).

**Coordinator gates are symmetric with agent gates.** A failed or empty tool result wrapper voids that verification pass: salvaged artifacts are provisional until re-derived or the pass re-runs, and a salvaged verdict never gates a merge alone. Routed residuals (a failed gate item re-routed as a question) must name the receiving ticket or owner call and record its acceptance in the trail; otherwise the item stays a merge blocker. Merge lines state the gate numbers (suites passed / failed against the named baseline) or say expected, not verified; verified separately without a number is not a record. The READY gate standard: 0 failed like-for-like in the worktree; baseline failures are named and cited, ticket-mandated failures are fixed before READY, and assertions that cannot be derived from the seed module's shape go back through FLAG.

**Hub integrity.** Check the line count after every append (wc -l before and after). Back the hub up to `.coordination/<round>-hub-backup.md` at each wave boundary. Lost lines are recoverable: agent sessions append via cat >>, so reconstruct from the agents' session jsonl files and archive under `.coordination/` with a provenance header.

**Amendment and commit discipline.** One artifact class per commit: skill text, registry rows, and snapshots never share a commit. The amendment number goes in the commit message, and every skill-repo commit gets a hub echo line. An amendment announced but not on disk does not exist: verify the file after writing, not the hub line.

After merges: reviewer-checked doc duties land on main with the merge; captures backed up before worktree teardown; branches deleted; issues flipped to done.

**PLAN.md lifecycle.** PLAN.md is an index, not a record. Open packets: one line each, what it is plus the gate. Closed or dropped packets: one line each, status plus a pointer (merge commit, report path, or issue file); trim closure prose at close time, never append it. The story lives in the hub, the issue files, or DECISIONS.md. At round close the whole file archives to `.coordination/legacy/plan-<date>.md` and the next round starts with a fresh PLAN.
