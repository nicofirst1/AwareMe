# Working on AwareMe

Orientation first: `AGENTS.md` (map), `spec.md` (the contract; §5.1 content rules, §13 hard constraints), `DECISIONS.md` (standing decisions). This skill covers HOW to work and verify here; those files cover WHAT is true.

## Setup

- Work in your assigned worktree; provision with `npm install --legacy-peer-deps --no-audit --no-fund`, then the expo-asset remedy from `DECISIONS.md` (`npm install expo-asset@57.0.16 --no-save`).
- Gates: `npm run typecheck`, `npx jest`, `npm run lint`. Baselines live in the round hub; compare like-for-like (your worktree's node_modules, not main's).
- Emulator: `./scripts/emulator.sh` (bounded boot wait). APK: `./scripts/rebuild-android.sh`.

## Emulator work with pi-droid

Load the pi-droid skills for the tool sets: `android-screen` (perception), `android-interact` (input), `android-automate` (waits, find-and-tap, scroll-until-found). Check `android-plugin` for capabilities before hand-rolling them.

- The emulator (adb device) is a shared resource. In delegation rounds, claim `emulator-lock` in the round hub's STATUS LOG before device work and release after. Outside rounds, check nobody else is driving it.
- Lock discipline: a posted LOCK-CLAIM line is REQUIRED before ANY adb interaction, including emulator boot, kill, and reboot-recovery - recovering a frozen emulator is device work, not an exemption. Claims posted as NOTE lines (or not posted at all) are protocol breaches. After appending a claim, re-read the hub tail immediately: if a competing claim sits earlier in the file, the earlier claim wins (the hub is append-only; file order is authoritative when pane clocks drift - and they do, observed up to 15 minutes). A later claimant yields and re-queues. Never reinstall, wipe, or reboot the device while any other agent may hold the lock: a reinstall or `adb emu kill` destroys the holder's app state and capture work.
- Tap by text/id/element index from annotated screenshots, via pi-droid tools. Never guess pixel coordinates; raw `adb shell input tap x y` is a documented fallback only when a pi-droid tool genuinely cannot express the step, and the fallback must be disclosed in the evidence trail. `adb kill-server` (or any adb daemon restart) is a shared-singleton, lock-relevant event: it disconnects every concurrent adb user on the host. Take the emulator lock AND post a FLAG before running it; prefer non-destructive recovery (`adb devices`, re-connect) over kill-server, and never run it while another pane's captures are live.
- Restore device state after work: stop the app, stop Metro, `adb reverse --remove-all`, verify port 8081 is free. Claims of restoration must be verified commands, not intentions.

## Verification methodology: vision-first, hypothesis-driven

The failure mode this skill exists to prevent: wandering around the app clicking randomly, then writing claims from memory.

1. **Hypothesis first.** From the ticket, write the expected behavior as a checkable statement before touching the device ("the DayField opens a weekday list with capitalized names").
2. **Targeted interaction.** Drive straight to the surface that tests the hypothesis. Every tap/scroll answers a stated question; if you cannot say what question a step answers, do not take it.
3. **Capture.** Annotated screenshot + UI-tree dump for every claim. Pull a bounded logcat window around any crash/ANR or intent launch.
4. **Look at it.** The capture must be SEEN by a vision-capable reader before anything is claimed. If your own session model renders images, read the capture yourself and describe what it actually shows (colors, layout, text) against the hypothesis. If it does not (text-only model: the read tool rejects image attachments), delegate the visual inspection to a vision-capable agent (registry agent "eyes" or equivalent) and record its description verbatim as the evidence. A claim backed only by "the flow worked" is not evidence.
5. **Classify.** Every claim in a report or comment states its evidence class: live observation, UI dump, capture file, or logcat, with the exact filename.
6. **Preserve.** Evidence lives under `.coordination/<round>-captures/` or the round's evidence dir: real files, no 0-byte stubs, no duplicate files cited as distinct observations. If two captures are identical, say so and cite one.

For color/layout claims: name the palette token from `src/constants/theme.ts` you expect, then verify the rendered pixels or the UI tree against it. Pixel-count scripts may supplement but never replace looking.

## Round protocol (delegated cycles)

The round hub (`.coordination/<round>.md`) is the durable record: timestamped one-line transitions, append-only. Blockers are FLAG lines, never notes. Heartbeat every ~30 min of work.

Cycle shape: impl agent → READY → reviewer (outcome: spec fit + gates) and methodology auditor (process, below), both fresh-context, both must approve → merge. The methodology auditor judges HOW the work was done — hypothesis discipline, capture quality, vision use, protocol compliance, ownership compliance — never whether the code is correct. Each auditor's verdict MUST end with one proposed audit axis for the next audits: the common failure case it believes the current axes would miss, stated as `Proposed axis: <name> — catches: <failure case>`; the coordinator folds accepted axes into future auditor charters, so each audit makes the next one sharper. Axes live with scores in `.claude/skills/methodology-auditor/axis_classification.md` (active set = top 5 by score; auditors propose and score, the coordinator prunes). Methodology findings that reveal a skill gap go to the coordinator, who folds them in; auditors and impl agents do not edit this skill mid-round. When the coordinator amends this skill, it posts a `SKILL-UPDATE` hub line and steers every working agent to re-read it; agents re-read the file on such a line before their next device interaction or claim, and audits judge against the amended text. Amendment discipline: every amendment is numbered (counted in the round hub); BEFORE applying one, the coordinator snapshots the current SKILL.md into `versions/<date>-r<N>-SKILL.md` in this skill's directory, and at every 3rd amendment reviews the axis registry (prune if more than 5 axes: drop the lowest score, oldest wins ties, sort the rest by score).

After merges: reviewer-checked doc duties land on main with the merge; captures backed up before worktree teardown; branches deleted; issues flipped to done.
