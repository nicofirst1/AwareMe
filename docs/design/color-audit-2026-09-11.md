Write.tsx, Export, session-detail, and Review could not be reached this session — `idb` input started dropping taps intermittently partway through the run (Expo Go/idb known flakiness, not app-side); everything below is grounded in the 8 screens actually captured plus a full read of `theme.ts` and every screen/component file cited.

Context: this app already went through one color-focused audit (`docs/design/ui-audit-2026-09-11.md`) and a gamification pass (`docs/design/gamification-proposal-2026-09-11.md`). Both shipped — `accent`, `CategoryColors`, `PressureColors`, `CelebrationColors`, `Radius`, `Card`/`Button`/ `FilterChip`/`BadgeCard` all exist in the codebase today. The owner's "mostly black and white" verdict is a post-implementation reaction, not a request to start over: the infrastructure is there but under-deployed. This audit is about turning existing, already-AA-checked tokens up, not inventing a new palette.

## 1. Current-state findings

**Home (`01-home-light.png`, `10-home-dark.png`, `src/app/index.tsx`).** One `accent` pixel on the whole screen: the "Start writing" button (`index.tsx:111`, `styles.primaryButton:181`). The six `SECONDARY_LINKS` tiles (`index.tsx:59`, rendered `:139-140`) are flat `theme.backgroundElement` with `textSecondary`-grey icons — Stems, History, Review, Progress, Settings, Export all read as one undifferentiated grey wall, in both themes. In dark mode this is worse: `backgroundElement` (`#212225`) is so close to pure black that the tiles nearly disappear into the background (`10-home-dark.png`). This is the single highest-impact screen for the owner's complaint — it's the first thing every session shows, and 6 of its 7 interactive elements carry zero hue.

**Progress (`02-progress-light.png`, `src/app/progress.tsx`).** This is the screen purpose-built to be the app's one "reward" moment, and it reads as the second-most monochrome screen after Settings. `CelebrationColors.glowSoft` (progress.tsx:82 via `badge-card.tsx:20`) tints earned badges at only 16% alpha — in the screenshot the two earned cards ("First Words", "Six Endings") are a barely-perceptible cream vs. the four unearned cards' flat grey; a user skimming the grid cannot tell at a glance which badges are earned without reading text. `CelebrationColors.glow` (the actual gold, `#E8B34A`) is never used at all on this screen — no icon tint, no card edge — even though `card.tsx:14-18`'s `accentColor` prop exists for exactly a left-edge stripe treatment and `glow` is explicitly documented (`theme.ts:134-135`) as safe for decorative icon/edge use. The stats block (`progress.tsx:68-76`, `StatLine` at `:92-100`) renders four/five numbers in plain `text` color — no accent, despite being the screen's "peak" numbers.

**Stems (`03-stems-light.png`, `src/app/stems.tsx`).** The best screen in the app today color-wise: category chips and per-row left-edge stripes both use `CategoryColors`. But two of the five visible rows have no category set (seed data gap, not a code bug) and render as flat grey boxes identical to pre-audit — makes the still-monochrome rows look like a regression next to the colored ones. More important, the _category filter chips_ above the list (`stems.tsx`, via `FilterChip` `category` prop) only carry color when **selected**; unselected chips are a hairline-bordered outline in the category hue at low visual weight (`filter-chip.tsx:48`, `borderColor: chipColors.bg` — a light tint, not the saturated `.text` color) — six chips sit there mostly grey until tapped.

**Stem edit (`04-stem-edit-light.png`, `src/app/stem-edit.tsx`).** Same pattern as the filter chips: the category picker's unselected options ("None", "awareness", "self_acceptance", etc.) are near-invisible pale outlines; only the selected "integrity" chip shows real color. "How often" (Less often/Normal/More often) and the Archive/Delete text links are pure grey/black — no color role for the "Save" button's sibling actions.

**History (`05-history-light.png`, `11-history-dark.png`, `src/app/history.tsx`).** `SessionRow`'s `accentColor` stripe (`history.tsx:204-208`) only appears when the session's stem has a category — the first visible row here has none and shows a flat grey card identical to every other UI element on the page; the second row's "assertiveness" stripe is real but **measures 1.15:1 contrast against the card's own `backgroundElement` fill in light mode and 1.17:1 in dark mode** (computed via WCAG relative luminance — pale category `.bg` swatches sitting on a card that's already a similarly pale grey). The stripe is not a text pairing so it isn't bound by the 4.5:1 rule, but 1.15:1 means it is, in practice, invisible as a scanning aid — the very thing it exists to provide. Date-range and Stem filter chips are the same low-weight grey treatment as everywhere else (no `category` prop passed to those particular `FilterChip` instances).

**Settings (`07-settings-light.png`, `src/app/settings.tsx`).** Confirmed still exactly what the prior audit flagged: zero color anywhere except the (unseen this run, but code- verified) `error`-colored destructive block. `SectionHeader` (`settings.tsx:243`, `:288`, `:395`, `:413`) now exists and gives "SESSION"/"NOTIFICATIONS" a labeled eyebrow, which is a hierarchy win, but it's grey-on-white with a plain hairline rule — no color differentiates one section block from the next on a screen that is, per the prior audit, "the longest in the app."

**Cross-cutting, both themes.**

1. `accent` is a single hex used in exactly one place per screen it appears on (Home's CTA, stem-edit's Save) — never on icons, never on numbers, never as a card tint outside that one button. The token was built to be "used sparingly," but sparingly has tipped into "used almost nowhere."
2. `CategoryColors` — the richest palette in the app — only activates on _selected_ filter-chip state and on session rows _if_ the underlying stem has a category. Both gating conditions mean color is conditional and inconsistent rather than a structural signal a user can rely on screen-to-screen.
3. `CelebrationColors` ships but is nearly unused: `glowSoft` alone, at 16% alpha, no `glow` gold anywhere. The app's one explicitly-sanctioned "delight" moment (`gamification-proposal-2026-09-11.md §2`) is visually the flattest reward screen in the app.
4. Dark mode amplifies every finding above: `backgroundElement`/`backgroundSelected` (`#212225`/`#2E3135`) sit close enough to `background` (`#000000`) that flat-grey UI nearly vanishes, and the same 16%-alpha `glowSoft`/1.15:1 stripe problems that are merely weak in light mode become close to invisible in dark.
5. Icons throughout (`@expo/vector-icons`, already installed — no new dependency needed) are uniformly `textSecondary`/`text` grey. Every home tile, section header, and badge card icon is monochrome; none carry `accent` or category color even where one would be unambiguous (e.g. the Stems tile's leaf icon, the Progress tile's trophy icon).

None of this is a violation of the writing-screen restraint (write.tsx wasn't reachable this session, but its existing `PressureColors` treatment is out of scope for this audit's complaint — pressure color is correctly functional, not decorative, and should stay untouched). The "black and white" complaint is squarely about the chrome screens: Home, Stems, History, Settings, Progress.

## 2. Proposed color direction

No new palette family. Every proposal below extends tokens that already exist and are already AA-proven; the fix is **distribution and opacity**, not invention.

**A. Icon tinting — the single highest-leverage change.** Home's six tile icons and Progress's badge icons get `accent` (not grey). This alone breaks the "wall of grey tiles" on the screen the owner starts every session from, with zero new tokens.

- `accent` as icon tint on `backgroundElement`: light `#B5541A` on `#F0F0F3` = **4.35:1** — under the 4.5:1 _text_ floor, which is fine, this is icon-only, not a text pairing (matches the existing `border`/`accentColor` "decorative, not text" precedent already established in `theme.ts`). Dark `#E8873F` on `#212225` = **6.04:1**, clear even as text if ever needed.

**B. `accentMuted` as the Home tile fill, not just card decoration.** `accentMuted` already exists (`theme.ts:32`/`:59`, documented as safe for card fills, not text) but is unused in the app today. Apply it as the fill for the Home tile that leads to the in-progress action ("Review available" / whichever tile is contextually relevant) — one tile gets a warm tint, the rest stay `backgroundElement`, giving Home an actual hierarchy cue beyond size, which was the exact gap the prior audit named (`ui-audit-2026-09-11.md §1`, "no hierarchy signal beyond size") and which shipping `Button variant="primary"` alone didn't fully close.

- No new hex: `accentMuted` light `#F6EAE4`, dark `#25160A`, already measured safe for `text`/`textSecondary` on top (17.81:1 / 5.04:1 light; 17.53:1 / 8.42:1 dark).

**C. `CelebrationColors.glow` promoted to actually decorate badges.** Give earned `BadgeCard`s a `glow`-colored left edge (via `Card`'s existing `accentColor` prop — zero new plumbing) in addition to the current `glowSoft` fill, and tint the badge's icon (once badges get icons — currently text-only, see cycle 2 below) with `glow`. This is the "peak moment" screen; it should look like one.

- `glow` (`#E8B34A`) as a decorative edge/icon: already measured in `theme.ts:134-135` — 10.98:1 on black (dark card edge, fine), 1.91:1 on white (light card edge, weak but it's a 3px stripe next to a `glowSoft` fill, not a lone element on pure white — same visual role `CategoryColors` stripes already play at comparable weakness, and unlike those, `glowSoft`'s cream fill sits directly behind it, lifting effective contrast).

**D. Fix the History/session-row stripe's real invisibility.** The 1.15:1/1.17:1 problem isn't a new-color problem, it's a _layering_ problem: `CategoryColors[*].bg` (a pale tint) sits on `backgroundElement` (also pale). Two fixes, no new hex needed — pick one per reviewer preference:

- **D1 (recommended, smallest diff):** widen the stripe from 3px to 4px and switch its color source from `.bg` to `.text` (the saturated half of each category pair, already computed and already ≥4.5:1 against _background_ — e.g. `integrity` dark text `#0E3D45` light / `#A9E4EF` dark). Recomputed: `#0E3D45` (integrity text) on `#F0F0F3` (light card) = **8.4:1**; `#A9E4EF` (integrity text, dark) on `#212225` (dark card) = **11.9:1**. Both comfortably visible. This changes one line in `history.tsx:204` (`.bg` → `.text`) and the equivalent in `stems.tsx`'s `StemRow`.
- **D2 (alternative):** keep `.bg` but move the stripe to sit against `background` (screen background) instead of `backgroundElement` (card fill) by extending it past the card's rounded corner — more layout churn for a marginal gain over D1; not recommended unless D1's saturated stripe reads as too strong against the currently pastel-only palette.

**E. Category color on Settings section headers — skip.** Considered threading `CategoryColors` into `SectionHeader`, rejected: Settings' sections (Session, Notifications, Writing, App) aren't stem categories, there's no natural color mapping, and forcing one would be decoration without meaning — the same trap the prior audit warned against ("fastest way back to a gamified rainbow"). Settings' fix is weight/rule color, not category hue: give `SectionHeader`'s rule (currently a plain `border`-colored hairline) an `accent`-tinted variant at low opacity, consistent across all four sections, not per-section colored.

**No new dependency anywhere** — every change above is a prop/token change on `Card`/`FilterChip`/`BadgeCard`/`Ionicons` (or whichever `@expo/vector-icons` family is already imported) via the `color` prop that component already accepts.

## 3. Cycle plan

Ordered by impact: Home first (the screen the complaint is actually about), then Stems/ History (richest existing palette, currently gated), then Progress (the reward screen), then Settings (lowest traffic, mechanical).

**Cycle 1 — Home hierarchy + icon color.** Files: `src/app/index.tsx` only. Changes: (a) tint all six `SECONDARY_LINKS` icons with `theme.accent` instead of `textSecondary` (icon color prop only, `index.tsx:139-140`'s render loop); (b) give the Progress tile (or whichever tile is contextually "next," e.g. Review when `reviewAvailable`) a `theme.accentMuted` background fill instead of `theme.backgroundElement`, keeping the other five tiles unchanged. Acceptance criteria (screenshot-checkable): Home's six tiles show visibly colored icons against grey fills (not grey-on-grey) in both light and dark screenshots; exactly one tile has a warm-tinted background, not all six or zero; "Start writing" remains the only full-`accent`-fill element (no competing saturation).

**Cycle 2 — Stems/History category color always-on.** Files: `src/components/filter-chip.tsx`, `src/app/history.tsx`, `src/app/stems.tsx`. Changes: (a) `filter-chip.tsx` — unselected category chips switch their border color source from `chipColors.bg` (pale) to `chipColors.text` (saturated), matching proposal D1's contrast fix, so unselected chips are visibly colored, not just selected ones; (b) `history.tsx`'s `SessionRow` and `stems.tsx`'s `StemRow` accent stripe: switch source from `.bg` to `.text` per proposal D1, width 3px → 4px. Acceptance criteria: category filter-chip rows in Stems/History show visible per-category outline color even before tapping (screenshot comparison against `03-stems-light.png`/ `05-history-light.png`); session/stem row stripes are clearly visible (not a near- invisible pastel line) against the card fill in both themes; rows with no category still render a plain card (no regression, no placeholder color invented for "no category").

**Cycle 3 — Progress screen celebration.** Files: `src/components/badge-card.tsx`, `src/app/progress.tsx`. Changes: (a) `badge-card.tsx` — earned cards get `accentColor={CelebrationColors.glow}` via the existing `Card` prop (left-edge stripe) in addition to current `glowSoft` fill; (b) `progress.tsx`'s `StatLine` values render in `theme.accent` instead of default `text` color (numbers are the "peak" content on this screen). Acceptance criteria: earned badges are unambiguously distinguishable from unearned ones at a glance in a screenshot (gold edge + tinted fill vs. plain grey card, silhouette opacity unchanged); the four stat numbers (Sessions/Endings/Stems written on/Longest streak) read in accent color, labels stay `textSecondary`; no numeric badge counter is introduced (still no "3/11", preserving the evaluation-free constraint); dark-mode screenshot confirms the gold edge is visible against `#212225` cards.

**Cycle 4 — Settings section rule + stem-edit/import category chip parity.** Files: `src/components/section-header.tsx`, `src/app/stem-edit.tsx`, `src/app/stem-import.tsx`. Changes: (a) `section-header.tsx` — rule color changes from plain `border` to a light `accent`-tinted hairline (same accent hue, low alpha, applied uniformly across all sections — not per-section colored, per finding E); (b) `stem-edit.tsx`/ `stem-import.tsx` category pickers pick up the same D1 fix from cycle 2 automatically once `filter-chip.tsx` changes (verify only, likely no code change needed here beyond confirming both files already pass `category` to `FilterChip` — check before editing). Acceptance criteria: Settings' four section rules are visibly warmer than plain grey but still clearly secondary to `accent`'s CTA use (no section reads as "important" over another); stem-edit/stem-import category chips match stems.tsx's filter-chip contrast exactly (same component, same props, verified by side-by-side screenshot); `npm run typecheck`/`npm test` pass; no new dependency added anywhere across all four cycles.

**Cycle 5 (optional, only if 1–4 still read as insufficiently colorful after review) — Write-screen ambient tint.** Not proposed as a required cycle: the writing screen's restraint is a spec-level constraint (§10, "color there must serve focus/pressure, not decoration"), and the owner's complaint was about the chrome screens, not the writing screen, per the task framing. If cycles 1–4 are judged insufficient, the only defensible addition here is a very low-alpha `accentMuted` wash behind the _stem text itself_ (not the input, not the button) — reviewers should treat this cycle as discretionary and revisit only after 1–4 ship and are judged against real screenshots.

Total scope: cycles 1–4 are small, independently committable, ordered by screen traffic; each is a same-file or two-file diff with no new component and no new token beyond what `theme.ts` already ships. Cycle 5 is explicitly optional and should not be started without a fresh review of cycles 1–4's screenshots first.
