# Morning/evening sessions replace random single-stem draws

A session is no longer one stem chosen at random from the active pool (the old spec §6.2 weighted draw with recency/category penalties). Every stem now carries a `time_of_day` ('morning' | 'evening' | null, migration 0003). Starting a session loads _every_ active stem tagged for the chosen period and presents them one at a time as a sitting — the sitting is complete only once all of them have been written. Selection is now purely `getActiveStemsForTimeOfDay(timeOfDay)`: no weighting, no randomness, no seed. `src/session/stemSelection.ts` (the weighted-draw machinery) is deleted, not deprecated — nothing is left to select between once "all of them" is the answer.

Notifications follow the same shape: two repeating daily local notifications (`expo-notifications`' native `SchedulableTriggerInputTypes.DAILY`, `{ hour, minute }`), one at `morning_notification_time` and one at `evening_notification_time` (both user-set "HH:MM", §7). The OS repeats these in local wall-clock time on its own, so there is no fire-time math, no 90-minute gap rule, no rolling horizon, and no 64-pending cap left to own in-app — `src/notifications/scheduling.ts` (the old random/fixed fire-time generator) is deleted along with it. Rescheduling is a plain cancel-all-then-recreate-both, not a diff, since there are only ever these two fixed-identifier notifications. Notification copy stays content-free (§6.4's lock-screen-privacy MUST is unchanged): distinct neutral copy per period, never stem or user text.

A sitting has no row of its own in the schema. `sessions` stays exactly what it was — one row per stem, per ADR-0001's momentum rules and `stem_text_snapshot`'s denormalisation (CLAUDE.md) — because a sitting is a sequence of those rows, not a new kind of event; giving it its own table would contradict the append-only, one-row-per-writing-event shape the rest of spec §4 is built on, and would silently break history/export/review's existing "session = one stem's timed writing" assumption. `write.tsx` owns the sequence itself, purely in component state: a queue of stems for the period, recomputed fresh on every mount (never persisted), driving the existing single-stem `useWritingSession` hook once per stem. Resuming after a cold start (ADR-0001's 5-minute grace) reconstructs the queue _position_, not just the one open session, by finding which period's active-stem list the open session's `stem_id` belongs to — an interrupted sitting still finishes the stems after the one that was open, rather than truncating there.

The post-session badge/celebration (gamification pivot, 2026-09-11) fires once, after the _whole_ sitting's last stem reaches `done` — never between stems, never during writing, unchanged from the existing "never during writing" boundary.

`notification_schedule` and `stems.weight` are left in the schema, vestigial but not removed — no migration in this slice; see DECISIONS.md's 2026-09-14 entry for what's still wired to each. Pre-migration and untagged stems (`time_of_day IS NULL`) are not backfilled; they simply never appear in a sitting until tagged.

This supersedes the random-notification aspects of prior decisions recorded elsewhere in DECISIONS.md (the 2026-09-11 "fixed mode" addition and the original random-window scheduler); it does not touch ADR-0001 (session momentum/resume), which this pivot's resume-queue logic builds directly on top of.
