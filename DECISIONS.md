# Decisions

Deviations from `spec.md` and resolutions of its open questions (§14). The spec (§0) requires deviations be justified here.

## Resolved open questions (§14)

1. **Session resumability** — Sessions are never manually resumable; momentum is sacred. Auto-resume only within a 5-minute wall-clock absence grace, uniform across backgrounding and cold start. See ADR-0001.
2. **On-demand stem repeat** — Yes. The library can start a session on a chosen stem, bypassing weighted selection (`origin = 'manual'`).
3. **Per-stem note/tag** — No. Stems carry text + one optional `category` only. See ADR-0002.
4. **Review period** — Default 7 days, selectable at review time from presets (7 / 14 / 30). The weekly prompt stays weekly; the `reviews` table already stores explicit `period_start`/`period_end`.

## Deviations from the spec schema (§4.2)

These follow from resolving §14 Q1 and are M1 schema changes; each still gets a migration and a `schema_version` bump per §13.8. See ADR-0003.

- **`endings.submitted_at` is nullable** (spec DDL says `NOT NULL`). A row with `submitted_at IS NULL` is an ending begun but not yet submitted.
- **`endings` rows are created on first keypress**, not on submit (spec §6.3.4). Captures true `started_at` and survives a hard kill via debounced autosave of the in-progress text.
- **New column `sessions.last_activity_at TEXT`**, bumped on the autosave debounce, so `absence = now − last_activity` is computable across a cold start.

## Scaffolding (ticket 01)

- **No web target.** Spec §2/§3 scope this app as iOS + Android only. `create-expo-app`'s default template ships React Native Web support (`react-native-web`, `react-dom`, a `web` block in `app.json`); removed both, since spec never asks for a browser target and carrying it is unused weight, not a hedge.
- **`expo-linking` added**, though not named in spec §3's dependency table. It is a hard runtime peer of `expo-router` (app fails to bundle without it) rather than a discretionary addition — recorded here for completeness, not as a deviation from intent.
- **Stripped the default template's demo app** (tabs, animated icon, hint rows, web badge, `react-native-reanimated`, `react-native-gesture-handler`, `react-native-worklets`, `@expo/ui`, `expo-glass-effect`, `expo-symbols`, `expo-image`, `expo-device`, `expo-web-browser`) down to a single `expo-router` home route, matching spec §10's "restrained, text-first, quiet" direction and the ticket's "shows a home screen" scope. None of the removed packages are requested anywhere in spec.md.

## Schema and migrations (ticket 02)

- **`expo-crypto` added**, not in spec §3's dependency table. UUIDv7 (§4.1.4, hard requirement) needs a real random-bytes source; neither `react-native` nor Expo SDK 57 polyfills `crypto.getRandomValues` on Hermes without it. It is a local, offline, no-network Expo native module — same category as `expo-linking`, not a discretionary addition. `src/db/uuidv7.ts` itself stays a pure function of injected time and randomness (unit tested deterministically); `src/db/id.ts` is the one call site that binds it to `expo-crypto`.
- **Migration tests run against `node:sqlite`** (Node 22.5+ builtin), not against `expo-sqlite` directly — `expo-sqlite` is a native module with no JS-only implementation, so it cannot execute inside plain Jest without a device/simulator. Production code (`src/db/migrate.ts`, future repositories) is written against a small `SqlExecutor` interface that `expo-sqlite`'s `SQLiteDatabase` satisfies structurally (checked at compile time by `src/db/executorCompat.check.ts`); tests adapt `node:sqlite` to the same interface. Both are real SQLite, so migration SQL is exercised against real engine semantics either way, not a mock.

## Seed content (ticket 03)

- **The two stems under spec §5.3's "general" heading are seeded with `category = null`.** Spec §5.2 defines exactly six categories (`awareness`, `self_acceptance`, `responsibility`, `assertiveness`, `purpose`, `integrity`) and "general" is not one of them, yet §5.3 groups stems #25–26 under a "general" heading. Rather than invent a seventh category or force these into one of the six, they're seeded with no category — the schema comment for `stems.category` already says "nullable for user stems," and this reads as the same escape hatch. If a later ticket wants `general` promoted to a real category, that's a schema/spec decision to make deliberately, not one to guess into a seed script.
- **All 26 stem texts and 3 meta-stem texts were checked programmatically, byte-for-byte, against spec.md §5.3–5.4** (not retyped by eye) before being committed, since fidelity to that exact original text — not Branden's — is the hard constraint in §5.1.

## Writing session (ticket 04)

- **`sessions.device_locale` is read via `Intl.DateTimeFormat().resolvedOptions().locale`**, not a new dependency (e.g. `expo-localization`). This is the same stdlib API already used for `created_tz`/`tz` in `src/db/time.ts`, works under Hermes without a native module, and spec §4.2 only asks for a locale string, not a full i18n API surface.
- **Session state lives in a plain hook (`src/session/useWritingSession.ts`), not a Zustand store.** A session is scoped to one screen's lifetime — nothing else in the app reads it mid-session — so global shared state would be unused flexibility. `sessionMachine.ts` (the reducer) and the repository calls it drives are unit tested directly; the hook is thin glue.
- **The stem-selection screen (`src/app/pick-stem.tsx`) is the "temporary picker" ticket 04 explicitly allows** ("a minimal way to reach the session on a chosen stem"). It lists all active stems with no weighting, filtering, or search — that's ticket 06/07's weighted selection and stem library, not this ticket's concern.

## Uncensored mode and interruption lifecycle (ticket 05)

- **Uncensored mode's backspace-within-word rule is enforced twice, deliberately redundantly.** `TextInput`'s `contextMenuHidden` prop disables cut/copy/paste/select at the OS level, which is what keeps the caret pinned to the end of the text in practice. `src/session/uncensoredEdit.ts#applyEdit` re-derives the same rule from the two text values (before/after) without trusting the caret, rejecting any shrink that isn't a single trailing character — so the restriction holds even if a future RN version, platform, or accessibility tool routes an edit around the disabled context menu. `backspace_count` increments in both modes; only _what's allowed_ differs by mode, per spec §6.3.6.
- **"Cannot navigate back to an earlier ending" is enforced structurally, not with a guard.** Submitted endings render as plain `ThemedText`, never as an editable/focusable control, so there is no affordance to select and no code path that could re-open one — narrower than an if-check that could later be relaxed by mistake.

## Weighted stem selection (ticket 06)

- **`selectStem` seeds its own deterministic PRNG (`mulberry32`) from a plain numeric seed**, rather than the caller passing pre-drawn randomness. Spec §6.2 requires selection to be "a pure function of (candidates, history, now, seed)" — a numeric seed in, a reproducible draw out, is the literal reading of that requirement and keeps the unit tests trivial (same seed ⇒ same stem, always). The category-recency boost (§6.2 "SHOULD lightly prefer") is implemented as a flat ×1.3 multiplier on any category not seen in the last 14 days; the spec only says "lightly," not by how much, so this is a judgement call, not a hidden deviation.
- **The category boost only applies to non-null categories.** The two "general" seed stems (`category = null`, see the ticket-03 entry above) are never boosted or penalised by category — there's no category to have gone unseen.
- **`Repository.getRecentStemUsage()` looks back 14 days**, the widest window either the recency or category penalty needs; the selection function itself does the day-boundary math, the query is just a cheap pre-filter.
- **The home screen's "Start now" imports `@/db` (and therefore `expo-sqlite`) eagerly** but only _calls_ `getRepository()` inside the button's press handler, not at render time, so `openDatabaseSync` never runs during the existing render-only smoke test.
- **Found and fixed in passing: `expo-asset` (a transitive dependency of `expo` itself, per `package-lock.json`) was missing from `node_modules`** despite being declared — a pre-existing partial-install gap that predates this ticket, surfaced the moment a component test (`index.test.tsx`) first exercised a code path reaching `@/db` → `expo-sqlite` → `expo-asset`. Fixed by reinstalling (`npm install expo-asset@57.0.16 --no-save --legacy-peer-deps`, chosen over a bare `npm install` because the latter rewrote hundreds of unrelated lockfile entries' `dev`/`devOptional` metadata for no functional change). Neither `package.json` nor `package-lock.json` changed; this is a `node_modules` repair, not a dependency addition.

## Stem library (ticket 07)

- **`src/app/pick-stem.tsx` (ticket 04's placeholder) is deleted**, superseded by `src/app/stems.tsx` exactly as ticket 04's own comment said it would be ("Superseded by the real stem library and weighted selection in M3"). `write.tsx`'s stem lookup was repointed from `listActiveStems()` to `listAllStems()` (excluding soft-deleted) so a session can still be started on an _archived_ stem reached via the library — archived only means "excluded from the weighted rotation" (schema comment on `stems.active`), not "unreachable," and the library is explicitly outside that rotation (§6.6 is a separate list from §6.2's draw).
- **Soft-deleted stems are shown in the library (for the "all" state filter) but not writable.** The row renders disabled/dimmed rather than being hidden — ticket 07 asks for "archived and soft-deleted stems handled correctly," and hiding deleted rows entirely would make the library disagree with the append-only/soft-delete principle (§4.1.5: deletion is a flag, not an absence).
- **The filter/search predicate lives in `src/session/stemLibraryFilter.ts` as a pure function**, not inlined in the screen, purely so it has one direct unit test — matching the existing pattern of keeping non-trivial logic (`sessionMachine.ts`, `uncensoredEdit.ts`, `stemSelection.ts`) outside the component tree. No screen-level render test was added for `stems.tsx`: `getRepository()` runs eagerly at mount (the screen needs its data immediately, unlike home's click-triggered lookup), which calls real `expo-sqlite`'s `openDatabaseSync` — unusable under Jest/`react-test-renderer` without a device or simulator, the same ceiling recorded in the ticket-02 entry above for why migration tests run against `node:sqlite` instead. This is consistent with the rest of the codebase: no existing test renders a screen that touches `@/db` at render time.
- **`node_modules/expo-asset` went missing again mid-ticket 07/08**, after an unrelated `npm install`/`uninstall` cycle (see the ticket-08 entry below) reconciled `node_modules` against the lockfile a second time. Fixed the same way (`npm install expo-asset@57.0.16 --no-save --legacy-peer-deps`); flagging that this gap is apparently not stable across reinstalls in this environment — a future agent hitting the same `Cannot find module 'expo-asset'` Jest failure should reach for this fix rather than adding it to `package.json`, which would misrepresent it as a direct dependency it isn't.

## Stem authoring (ticket 08)

- **Considered adding `expo-document-picker` for "open a `.txt` file" (§6.6), then didn't.** `expo-file-system` — already in spec §3's dependency table and already installed — ships `File.pickFileAsync()` in the SDK 57 line already pinned here, which opens the system file picker and returns a `File` (implements `Blob`, so `.text()` reads its contents). That covers the requirement with zero new dependencies; `expo-document-picker` was installed, exercised, and then removed once this was confirmed (`package.json`/`package-lock.json` are unchanged from before ticket 08).
- **Bulk import commits unconditionally when the user taps Import** — the preview (line list + live count, both already on screen before the tap) _is_ the "preview + count before committing" the spec asks for; there's no separate confirmation step because the preview isn't hidden behind the button, it's continuously visible above it.
- **The three-way weight control is available on both add and edit**, not edit-only. Spec §6.6 doesn't gate it to editing, and default-then-immediately-reweight is one extra tap saved for a user who already knows a new stem should be rare or frequent.
- **Archive and soft-delete both live on `/stem-edit`, gated on `?id=`, rather than as swipe actions on the library rows.** Swipe-to-reveal-actions isn't a built-in RN primitive without a gesture library (spec §3 doesn't list one, and the existing codebase has deliberately avoided `react-native-gesture-handler` — see the ticket-01 scaffold entry above), so the lazy option already-in-the-codebase is a plain screen with plain buttons, consistent with every other action-taking surface in this app (`write.tsx`, `stems.tsx`).
- **Soft-delete shows a confirmation (`Alert.alert`) with the "past sessions remain" language the ticket asks for; archive does not.** Archive is explicitly "the primary destructive action" in spec §6.6 but is fully reversible (toggled back with the same control) and excluded only from the weighted draw, not from the library or export — a confirmation for a reversible, low-stakes toggle would be the kind of friction the app's "no gamification, no anxiety" design direction (§10) argues against. Delete is soft but one-way in the UI (no "undelete" control), so it keeps the confirmation.

## Notification scheduling logic (ticket 09)

- **`mulberry32` (the seeded PRNG ticket 06 wrote for `selectStem`) was extracted to `src/lib/prng.ts`** so `src/notifications/scheduling.ts` could reuse it rather than duplicate a second copy. Both call sites need the same thing — a plain-number-seeded, deterministic `() => number` generator — and the spec's determinism requirement for scheduling (§6.4, mirroring §6.2's "pure function of a random seed") is identical in shape to stem selection's. `stemSelection.ts`'s public API and tests are unchanged; only the private helper moved.
- **DST correctness (§11) uses no date library.** `generateFireTimes` builds each day's window with `new Date(year, month, date, hour, minute)` — the local-time `Date` constructor — rather than adding milliseconds to a UTC midnight. The JS engine resolves those local wall-clock fields against the host's IANA timezone data itself (verified under Node with `TZ=Europe/Berlin` across both the spring-forward and fall-back 2026 transitions: an 08:00–21:00 window stays 08:00–21:00 local on the transition day even though the UTC gap isn't 13 hours that day). This is the native-platform-feature rung: no new dependency, and it is correct on the DST edge cases the spec's own test list (§11) names, not just the common case.
- **The 90-minute minimum gap is enforced globally across a calendar day, across all configured windows**, not independently per window. Spec §6.4 says "a minimum 90 minute gap between them" without scoping "them" to one window; two windows on the same day (e.g. a morning and an evening block) could otherwise each independently place a time within 90 minutes of the window boundary and violate the gap in aggregate. Draws are sequenced through one shared PRNG stream and rejection-sampled against every time already accepted that day, regardless of which window it came from.
- **`generateFireTimes` is a pure "compute the ideal schedule from scratch" function, not a stateful diff/merge against `notification_schedule`.** The ticket's "rescheduling is idempotent" is read as: identical inputs (including `now` and `seed`) always produce identical output — proven directly by a test that calls it repeatedly and compares results. Reconciling that output against already-scheduled/already-fired rows in `notification_schedule` (cancel superseded, keep what's still valid, top up the gap) is integration behaviour with real state and a real clock, and belongs to ticket 10, not this pure module.
- **A narrow or over-subscribed window degrades by returning fewer times than requested, not by throwing or looping forever.** `drawTimesInWindow` caps rejection-sampling attempts at `count * 200`; a window too short to fit the requested count at ≥90-minute spacing just yields as many as fit. No ticket asked for an error path here, and silently under-filling is strictly better than a hang for a background scheduling call.
- **`diffSchedule` (also in `scheduling.ts`) was added alongside `generateFireTimes` as a second pure function**, matching a time already pending (within a 60-second tolerance) to a time still wanted, so ticket 10's integration layer can reconcile without re-deriving this matching logic itself or duplicating it untested. It stays in the ticket-09 file because it has the same purity/testability shape as `generateFireTimes` (no SQLite, no clock, no `expo-notifications`) even though the ticket that actually calls it is 10.

## Notifications integration (ticket 10)

- **The stem for a notification is chosen once, at schedule time, not at fire or tap time.** `rescheduleNotifications` (`src/notifications/scheduler.ts`) calls `selectStem` (06) for every newly-created fire time and stores the result on that `notification_schedule` row; tapping the notification later (`useNotificationTapRouting`) reads the row back by the OS identifier the tap carries rather than drawing again. The ticket's "the stem is chosen at fire time via selection (06)" is read this way because the schedule is necessarily computed ahead of the OS actually firing it (that's the whole point of scheduling), and the `notification_schedule.stem_id` column already exists in spec §4.2's own DDL for exactly this purpose — a nullable FK filled in by the scheduler, not left for the tap handler to resolve blind.
- **Reschedule triggers actually wired: app foreground (mount + `AppState` → `'active'`) and permission grant (calling `requestNotificationPermission()` and then `rescheduleNotifications()` is the same two-call sequence any future caller — onboarding, ticket 17 — would use).** "Settings change" and "timezone change" (also named in §6.4) have no call site yet because no settings screen exists in this codebase (ticket 16 is unbuilt) and RN/Expo have no cross-platform timezone-change event without a further native dependency. `rescheduleNotifications()` itself is the complete, idempotent, side-effect-safe entry point ticket 16's settings screen should call on save — this is the seam, not a gap to paper over with an unused listener. Timezone changes are covered incidentally: `generateFireTimes` always reads the device's _current_ local timezone via the plain `Date` constructor (no cached offset anywhere), so the very next foreground reconcile after a timezone change recomputes windows correctly, even with no explicit TZ-change listener.
- **`useNotificationScheduler`'s reschedule call is wrapped in a `.catch` that only warns in `__DEV__`.** Spec §9 requires the app to keep working fully standalone; a native-module hiccup scheduling notifications (e.g. running on a bare simulator without full native config) must never crash app startup or a foreground transition. This is the one place in the notifications integration where a try/catch was added deliberately, over the thin-glue-stays-thin default, because the failure mode (unhandled promise rejection on every foreground) is a real regression risk for something users never see either way.
- **Foreground presentation shows the banner (`shouldShowBanner: true`) rather than suppressing it.** The content is already neutral by construction (`NOTIFICATION_BODY = 'A sentence is waiting.'`, no stem or user text ever placed in `content`), so there's nothing left to protect by hiding the in-app banner — suppressing it would just be inconsistent with what the lock screen already shows.
- **`app.json` gained the `expo-notifications` config plugin entry (no custom options)**, matching the existing pattern for `expo-splash-screen`. All its options (Android icon/color, iOS background mode) are optional with sane defaults; `enableBackgroundRemoteNotifications` defaults to `false`, which is correct here since this app never does remote/background push. Not a new dependency — the package was already installed; this only adds its native config step, without which Android notification channel/icon defaults would be less deliberate.
- **`useWritingSession.start()` and `StemForSession` gained optional `origin`/`notificationId`/`notifiedAt` fields**, defaulting to `origin: 'manual'` so ticket 04/06's existing call sites (`index.tsx`, `stems.tsx`) are unchanged. `write.tsx` reads `origin`/`notificationId`/`notifiedAt` from route params (present only on the notification deep link) and threads them through, so `sessions.origin`, `.notification_id`, and `.notified_at` are set correctly without a second code path for "how a session gets created."
- **No onboarding or settings UI was added.** Ticket 10 is blocked by 09/06/04, not by 16 (settings) or 17 (onboarding); `requestNotificationPermission()` and `rescheduleNotifications()` are exported specifically so those future screens are one call each, not a redesign. There is currently no in-app way for a user to grant notification permission — that's ticket 17's onboarding flow, not a gap in this ticket's own scope.
