# Decisions

Deviations from `spec.md` and resolutions of its open questions (§14). The spec (§0) requires deviations be justified here.

## Resolved open questions (§14)

1. **Session resumability** — Sessions are never manually resumable; momentum is sacred. Auto-resume only within a 5-minute wall-clock absence grace, uniform across backgrounding and cold start. See ADR-0001.
2. **On-demand stem repeat** — Yes. The library can start a session on a chosen stem, bypassing weighted selection (`origin = 'manual'`).
3. **Per-stem note/tag** — No. Stems carry text + one optional `category` only. See ADR-0002.
4. **Review period** — Default 7 days, selectable at review time from presets (7 / 14 / 30). The weekly prompt stays weekly; the `reviews` table already stores explicit `period_start`/`period_end`.

## Deviations from the spec schema (§4.2)

These follow from resolving §14 Q1 and are M1 schema changes; each still gets a migration and a `schema_version` bump per §13.8. See ADR-0003.

- **`endings.submitted_at` is nullable** (spec DDL says `NOT NULL`). A row with `submitted_at IS NULL` is an ending begun but not yet submitted.
- **`endings` rows are created on first keypress**, not on submit (spec §6.3.4). Captures true `started_at` and survives a hard kill via debounced autosave of the in-progress text.
- **New column `sessions.last_activity_at TEXT`**, bumped on the autosave debounce, so `absence = now − last_activity` is computable across a cold start.

## Scaffolding (ticket 01)

- **No web target.** Spec §2/§3 scope this app as iOS + Android only. `create-expo-app`'s default template ships React Native Web support (`react-native-web`, `react-dom`, a `web` block in `app.json`); removed both, since spec never asks for a browser target and carrying it is unused weight, not a hedge.
- **`expo-linking` added**, though not named in spec §3's dependency table. It is a hard runtime peer of `expo-router` (app fails to bundle without it) rather than a discretionary addition — recorded here for completeness, not as a deviation from intent.
- **Stripped the default template's demo app** (tabs, animated icon, hint rows, web badge, `react-native-reanimated`, `react-native-gesture-handler`, `react-native-worklets`, `@expo/ui`, `expo-glass-effect`, `expo-symbols`, `expo-image`, `expo-device`, `expo-web-browser`) down to a single `expo-router` home route, matching spec §10's "restrained, text-first, quiet" direction and the ticket's "shows a home screen" scope. None of the removed packages are requested anywhere in spec.md.

## Schema and migrations (ticket 02)

- **`expo-crypto` added**, not in spec §3's dependency table. UUIDv7 (§4.1.4, hard requirement) needs a real random-bytes source; neither `react-native` nor Expo SDK 57 polyfills `crypto.getRandomValues` on Hermes without it. It is a local, offline, no-network Expo native module — same category as `expo-linking`, not a discretionary addition. `src/db/uuidv7.ts` itself stays a pure function of injected time and randomness (unit tested deterministically); `src/db/id.ts` is the one call site that binds it to `expo-crypto`.
- **Migration tests run against `node:sqlite`** (Node 22.5+ builtin), not against `expo-sqlite` directly — `expo-sqlite` is a native module with no JS-only implementation, so it cannot execute inside plain Jest without a device/simulator. Production code (`src/db/migrate.ts`, future repositories) is written against a small `SqlExecutor` interface that `expo-sqlite`'s `SQLiteDatabase` satisfies structurally (checked at compile time by `src/db/executorCompat.check.ts`); tests adapt `node:sqlite` to the same interface. Both are real SQLite, so migration SQL is exercised against real engine semantics either way, not a mock.

## Seed content (ticket 03)

- **The two stems under spec §5.3's "general" heading are seeded with `category = null`.** Spec §5.2 defines exactly six categories (`awareness`, `self_acceptance`, `responsibility`, `assertiveness`, `purpose`, `integrity`) and "general" is not one of them, yet §5.3 groups stems #25–26 under a "general" heading. Rather than invent a seventh category or force these into one of the six, they're seeded with no category — the schema comment for `stems.category` already says "nullable for user stems," and this reads as the same escape hatch. If a later ticket wants `general` promoted to a real category, that's a schema/spec decision to make deliberately, not one to guess into a seed script.
- **All 26 stem texts and 3 meta-stem texts were checked programmatically, byte-for-byte, against spec.md §5.3–5.4** (not retyped by eye) before being committed, since fidelity to that exact original text — not Branden's — is the hard constraint in §5.1.

## Writing session (ticket 04)

- **`sessions.device_locale` is read via `Intl.DateTimeFormat().resolvedOptions().locale`**, not a new dependency (e.g. `expo-localization`). This is the same stdlib API already used for `created_tz`/`tz` in `src/db/time.ts`, works under Hermes without a native module, and spec §4.2 only asks for a locale string, not a full i18n API surface.
- **Session state lives in a plain hook (`src/session/useWritingSession.ts`), not a Zustand store.** A session is scoped to one screen's lifetime — nothing else in the app reads it mid-session — so global shared state would be unused flexibility. `sessionMachine.ts` (the reducer) and the repository calls it drives are unit tested directly; the hook is thin glue.
- **The stem-selection screen (`src/app/pick-stem.tsx`) is the "temporary picker" ticket 04 explicitly allows** ("a minimal way to reach the session on a chosen stem"). It lists all active stems with no weighting, filtering, or search — that's ticket 06/07's weighted selection and stem library, not this ticket's concern.

## Uncensored mode and interruption lifecycle (ticket 05)

- **Uncensored mode's backspace-within-word rule is enforced twice, deliberately redundantly.** `TextInput`'s `contextMenuHidden` prop disables cut/copy/paste/select at the OS level, which is what keeps the caret pinned to the end of the text in practice. `src/session/uncensoredEdit.ts#applyEdit` re-derives the same rule from the two text values (before/after) without trusting the caret, rejecting any shrink that isn't a single trailing character — so the restriction holds even if a future RN version, platform, or accessibility tool routes an edit around the disabled context menu. `backspace_count` increments in both modes; only _what's allowed_ differs by mode, per spec §6.3.6.
- **"Cannot navigate back to an earlier ending" is enforced structurally, not with a guard.** Submitted endings render as plain `ThemedText`, never as an editable/focusable control, so there is no affordance to select and no code path that could re-open one — narrower than an if-check that could later be relaxed by mistake.

## Weighted stem selection (ticket 06)

- **`selectStem` seeds its own deterministic PRNG (`mulberry32`) from a plain numeric seed**, rather than the caller passing pre-drawn randomness. Spec §6.2 requires selection to be "a pure function of (candidates, history, now, seed)" — a numeric seed in, a reproducible draw out, is the literal reading of that requirement and keeps the unit tests trivial (same seed ⇒ same stem, always). The category-recency boost (§6.2 "SHOULD lightly prefer") is implemented as a flat ×1.3 multiplier on any category not seen in the last 14 days; the spec only says "lightly," not by how much, so this is a judgement call, not a hidden deviation.
- **The category boost only applies to non-null categories.** The two "general" seed stems (`category = null`, see the ticket-03 entry above) are never boosted or penalised by category — there's no category to have gone unseen.
- **`Repository.getRecentStemUsage()` looks back 14 days**, the widest window either the recency or category penalty needs; the selection function itself does the day-boundary math, the query is just a cheap pre-filter.
- **The home screen's "Start now" imports `@/db` (and therefore `expo-sqlite`) eagerly** but only _calls_ `getRepository()` inside the button's press handler, not at render time, so `openDatabaseSync` never runs during the existing render-only smoke test.
- **Found and fixed in passing: `expo-asset` (a transitive dependency of `expo` itself, per `package-lock.json`) was missing from `node_modules`** despite being declared — a pre-existing partial-install gap that predates this ticket, surfaced the moment a component test (`index.test.tsx`) first exercised a code path reaching `@/db` → `expo-sqlite` → `expo-asset`. Fixed by reinstalling (`npm install expo-asset@57.0.16 --no-save --legacy-peer-deps`, chosen over a bare `npm install` because the latter rewrote hundreds of unrelated lockfile entries' `dev`/`devOptional` metadata for no functional change). Neither `package.json` nor `package-lock.json` changed; this is a `node_modules` repair, not a dependency addition.

## Stem library (ticket 07)

- **`src/app/pick-stem.tsx` (ticket 04's placeholder) is deleted**, superseded by `src/app/stems.tsx` exactly as ticket 04's own comment said it would be ("Superseded by the real stem library and weighted selection in M3"). `write.tsx`'s stem lookup was repointed from `listActiveStems()` to `listAllStems()` (excluding soft-deleted) so a session can still be started on an _archived_ stem reached via the library — archived only means "excluded from the weighted rotation" (schema comment on `stems.active`), not "unreachable," and the library is explicitly outside that rotation (§6.6 is a separate list from §6.2's draw).
- **Soft-deleted stems are shown in the library (for the "all" state filter) but not writable.** The row renders disabled/dimmed rather than being hidden — ticket 07 asks for "archived and soft-deleted stems handled correctly," and hiding deleted rows entirely would make the library disagree with the append-only/soft-delete principle (§4.1.5: deletion is a flag, not an absence).
- **The filter/search predicate lives in `src/session/stemLibraryFilter.ts` as a pure function**, not inlined in the screen, purely so it has one direct unit test — matching the existing pattern of keeping non-trivial logic (`sessionMachine.ts`, `uncensoredEdit.ts`, `stemSelection.ts`) outside the component tree. No screen-level render test was added for `stems.tsx`: `getRepository()` runs eagerly at mount (the screen needs its data immediately, unlike home's click-triggered lookup), which calls real `expo-sqlite`'s `openDatabaseSync` — unusable under Jest/`react-test-renderer` without a device or simulator, the same ceiling recorded in the ticket-02 entry above for why migration tests run against `node:sqlite` instead. This is consistent with the rest of the codebase: no existing test renders a screen that touches `@/db` at render time.
- **`node_modules/expo-asset` went missing again mid-ticket 07/08**, after an unrelated `npm install`/`uninstall` cycle (see the ticket-08 entry below) reconciled `node_modules` against the lockfile a second time. Fixed the same way (`npm install expo-asset@57.0.16 --no-save --legacy-peer-deps`); flagging that this gap is apparently not stable across reinstalls in this environment — a future agent hitting the same `Cannot find module 'expo-asset'` Jest failure should reach for this fix rather than adding it to `package.json`, which would misrepresent it as a direct dependency it isn't.

## Stem authoring (ticket 08)

- **Considered adding `expo-document-picker` for "open a `.txt` file" (§6.6), then didn't.** `expo-file-system` — already in spec §3's dependency table and already installed — ships `File.pickFileAsync()` in the SDK 57 line already pinned here, which opens the system file picker and returns a `File` (implements `Blob`, so `.text()` reads its contents). That covers the requirement with zero new dependencies; `expo-document-picker` was installed, exercised, and then removed once this was confirmed (`package.json`/`package-lock.json` are unchanged from before ticket 08).
- **Bulk import commits unconditionally when the user taps Import** — the preview (line list + live count, both already on screen before the tap) _is_ the "preview + count before committing" the spec asks for; there's no separate confirmation step because the preview isn't hidden behind the button, it's continuously visible above it.
- **The three-way weight control is available on both add and edit**, not edit-only. Spec §6.6 doesn't gate it to editing, and default-then-immediately-reweight is one extra tap saved for a user who already knows a new stem should be rare or frequent.
- **Archive and soft-delete both live on `/stem-edit`, gated on `?id=`, rather than as swipe actions on the library rows.** Swipe-to-reveal-actions isn't a built-in RN primitive without a gesture library (spec §3 doesn't list one, and the existing codebase has deliberately avoided `react-native-gesture-handler` — see the ticket-01 scaffold entry above), so the lazy option already-in-the-codebase is a plain screen with plain buttons, consistent with every other action-taking surface in this app (`write.tsx`, `stems.tsx`).
- **Soft-delete shows a confirmation (`Alert.alert`) with the "past sessions remain" language the ticket asks for; archive does not.** Archive is explicitly "the primary destructive action" in spec §6.6 but is fully reversible (toggled back with the same control) and excluded only from the weighted draw, not from the library or export — a confirmation for a reversible, low-stakes toggle would be the kind of friction the app's "no gamification, no anxiety" design direction (§10) argues against. Delete is soft but one-way in the UI (no "undelete" control), so it keeps the confirmation.

## Notification scheduling logic (ticket 09)

- **`mulberry32` (the seeded PRNG ticket 06 wrote for `selectStem`) was extracted to `src/lib/prng.ts`** so `src/notifications/scheduling.ts` could reuse it rather than duplicate a second copy. Both call sites need the same thing — a plain-number-seeded, deterministic `() => number` generator — and the spec's determinism requirement for scheduling (§6.4, mirroring §6.2's "pure function of a random seed") is identical in shape to stem selection's. `stemSelection.ts`'s public API and tests are unchanged; only the private helper moved.
- **DST correctness (§11) uses no date library.** `generateFireTimes` builds each day's window with `new Date(year, month, date, hour, minute)` — the local-time `Date` constructor — rather than adding milliseconds to a UTC midnight. The JS engine resolves those local wall-clock fields against the host's IANA timezone data itself (verified under Node with `TZ=Europe/Berlin` across both the spring-forward and fall-back 2026 transitions: an 08:00–21:00 window stays 08:00–21:00 local on the transition day even though the UTC gap isn't 13 hours that day). This is the native-platform-feature rung: no new dependency, and it is correct on the DST edge cases the spec's own test list (§11) names, not just the common case.
- **The 90-minute minimum gap is enforced globally across a calendar day, across all configured windows**, not independently per window. Spec §6.4 says "a minimum 90 minute gap between them" without scoping "them" to one window; two windows on the same day (e.g. a morning and an evening block) could otherwise each independently place a time within 90 minutes of the window boundary and violate the gap in aggregate. Draws are sequenced through one shared PRNG stream and rejection-sampled against every time already accepted that day, regardless of which window it came from.
- **`generateFireTimes` is a pure "compute the ideal schedule from scratch" function, not a stateful diff/merge against `notification_schedule`.** The ticket's "rescheduling is idempotent" is read as: identical inputs (including `now` and `seed`) always produce identical output — proven directly by a test that calls it repeatedly and compares results. Reconciling that output against already-scheduled/already-fired rows in `notification_schedule` (cancel superseded, keep what's still valid, top up the gap) is integration behaviour with real state and a real clock, and belongs to ticket 10, not this pure module.
- **A narrow or over-subscribed window degrades by returning fewer times than requested, not by throwing or looping forever.** `drawTimesInWindow` caps rejection-sampling attempts at `count * 200`; a window too short to fit the requested count at ≥90-minute spacing just yields as many as fit. No ticket asked for an error path here, and silently under-filling is strictly better than a hang for a background scheduling call.
- **`diffSchedule` (also in `scheduling.ts`) was added alongside `generateFireTimes` as a second pure function**, matching a time already pending (within a 60-second tolerance) to a time still wanted, so ticket 10's integration layer can reconcile without re-deriving this matching logic itself or duplicating it untested. It stays in the ticket-09 file because it has the same purity/testability shape as `generateFireTimes` (no SQLite, no clock, no `expo-notifications`) even though the ticket that actually calls it is 10.

## Notifications integration (ticket 10)

- **The stem for a notification is chosen once, at schedule time, not at fire or tap time.** `rescheduleNotifications` (`src/notifications/scheduler.ts`) calls `selectStem` (06) for every newly-created fire time and stores the result on that `notification_schedule` row; tapping the notification later (`useNotificationTapRouting`) reads the row back by the OS identifier the tap carries rather than drawing again. The ticket's "the stem is chosen at fire time via selection (06)" is read this way because the schedule is necessarily computed ahead of the OS actually firing it (that's the whole point of scheduling), and the `notification_schedule.stem_id` column already exists in spec §4.2's own DDL for exactly this purpose — a nullable FK filled in by the scheduler, not left for the tap handler to resolve blind.
- **Reschedule triggers actually wired: app foreground (mount + `AppState` → `'active'`) and permission grant (calling `requestNotificationPermission()` and then `rescheduleNotifications()` is the same two-call sequence any future caller — onboarding, ticket 17 — would use).** "Settings change" and "timezone change" (also named in §6.4) have no call site yet because no settings screen exists in this codebase (ticket 16 is unbuilt) and RN/Expo have no cross-platform timezone-change event without a further native dependency. `rescheduleNotifications()` itself is the complete, idempotent, side-effect-safe entry point ticket 16's settings screen should call on save — this is the seam, not a gap to paper over with an unused listener. Timezone changes are covered incidentally: `generateFireTimes` always reads the device's _current_ local timezone via the plain `Date` constructor (no cached offset anywhere), so the very next foreground reconcile after a timezone change recomputes windows correctly, even with no explicit TZ-change listener.
- **`useNotificationScheduler`'s reschedule call is wrapped in a `.catch` that only warns in `__DEV__`.** Spec §9 requires the app to keep working fully standalone; a native-module hiccup scheduling notifications (e.g. running on a bare simulator without full native config) must never crash app startup or a foreground transition. This is the one place in the notifications integration where a try/catch was added deliberately, over the thin-glue-stays-thin default, because the failure mode (unhandled promise rejection on every foreground) is a real regression risk for something users never see either way.
- **Foreground presentation shows the banner (`shouldShowBanner: true`) rather than suppressing it.** The content is already neutral by construction (`NOTIFICATION_BODY = 'A sentence is waiting.'`, no stem or user text ever placed in `content`), so there's nothing left to protect by hiding the in-app banner — suppressing it would just be inconsistent with what the lock screen already shows.
- **`app.json` gained the `expo-notifications` config plugin entry (no custom options)**, matching the existing pattern for `expo-splash-screen`. All its options (Android icon/color, iOS background mode) are optional with sane defaults; `enableBackgroundRemoteNotifications` defaults to `false`, which is correct here since this app never does remote/background push. Not a new dependency — the package was already installed; this only adds its native config step, without which Android notification channel/icon defaults would be less deliberate.
- **`useWritingSession.start()` and `StemForSession` gained optional `origin`/`notificationId`/`notifiedAt` fields**, defaulting to `origin: 'manual'` so ticket 04/06's existing call sites (`index.tsx`, `stems.tsx`) are unchanged. `write.tsx` reads `origin`/`notificationId`/`notifiedAt` from route params (present only on the notification deep link) and threads them through, so `sessions.origin`, `.notification_id`, and `.notified_at` are set correctly without a second code path for "how a session gets created."
- **No onboarding or settings UI was added.** Ticket 10 is blocked by 09/06/04, not by 16 (settings) or 17 (onboarding); `requestNotificationPermission()` and `rescheduleNotifications()` are exported specifically so those future screens are one call each, not a redesign. There is currently no in-app way for a user to grant notification permission — that's ticket 17's onboarding flow, not a gap in this ticket's own scope.

## History (ticket 11)

- **Filtering (stem/category/date-range) is done in SQL (`Repository.listSessionsForHistory`), not as a client-side pure predicate** like `stemLibraryFilter.ts`. The stem library's candidate set is bounded (dozens of stems, all held in memory already); history is an append-only, unbounded, multi-year corpus by design (§4, the whole point of the schema), so filtering it in-memory would get slower forever while filtering it in SQL does not. `HistoryFilters` is a plain object of optional fields so the query builds only the WHERE clauses actually requested.
- **Soft-delete of a session does not touch its endings' `deleted_at`.** `endings.deleted_at` exists in the schema (spec §4.2) but nothing sets it yet — a session-level soft-delete already hides the session (and therefore its endings, via the join) from every read in `listSessionsForHistory`/`getSessionDetail`. Per-ending deletion isn't asked for by any ticket; wiring a cascade now would be speculative.
- **No `historyFilter.ts` pure module.** Unlike the stem library, there's no interesting branching logic to unit test in isolation here — the "filter" is four optional equality/range clauses assembled into SQL, already exercised directly by `repository.history.test.ts` against real SQLite. A pure wrapper function would just be indirection over string concatenation.

## Full-text search (ticket 12)

- **`node:sqlite` (Node 22.5+) supports FTS5 out of the box** — verified directly (`CREATE VIRTUAL TABLE t USING fts5(x)` succeeds against `:memory:`). This removes what the ticket flagged as a risk: migration/search tests run against the FTS5 index the same way every other migration test does, against real SQLite via `nodeSqliteExecutor`, no separate testing strategy needed. `expo-sqlite` also compiles SQLite with `-DSQLITE_ENABLE_FTS5=1` by default on both iOS and Android (`node_modules/expo-sqlite/ios/ExpoSQLite.podspec`, `android/build.gradle`) — confirmed by reading the vendored build config, not assumed — so no `app.json` plugin change was needed to turn it on.
- **`endings_fts` is an external-content FTS5 table** (`content='endings', content_rowid='rowid'`), not a standalone/contentless one: the indexed text lives once, in `endings.text`; the FTS table stores only the inverted index keyed by `endings.rowid` (SQLite's implicit rowid — `endings`'s `TEXT PRIMARY KEY` doesn't suppress it, confirmed empirically). This avoids a second copy of every ending's text sitting in the database.
- **Three `AFTER` triggers on `endings` (insert/update/delete) keep the index in sync**, migration 0002. Every write this app makes to `endings.text` — first keypress (insert), autosave debounce, submit, finalize (all updates), and a session-level soft-delete (an update of the _session_, not the ending, so it doesn't even touch `endings`) — goes through one of these, so the sync is structural, not something a future call site can forget. `Repository.rebuildEndingsFts()` (`INSERT INTO endings_fts(endings_fts) VALUES ('rebuild')`, FTS5's built-in rebuild command) is the escape hatch for writes that bypass the repository entirely, e.g. ticket 15's import restoring rows directly — exported now so that ticket doesn't have to invent it.
- **Soft-deleted endings are deliberately left in the FTS index and filtered out at query time** (`Repository.searchEndings` joins to `sessions`/`endings` and adds `deleted_at IS NULL`), rather than having the triggers remove a row from the index when `deleted_at` is set. This matches how every other read in this codebase excludes soft-deleted rows (`listActiveStems`, `listSessionsForHistory`, …) — one filtering convention, not two — and keeps the trigger set doing exactly one thing (mirror `endings.text`) rather than also encoding a business rule about visibility.
- **Search input is defended against FTS5's own query syntax**, not passed to `MATCH` raw. `toFtsMatchQuery` splits on whitespace, double-quotes each term (escaping embedded `"`), and ANDs them — so a search for text containing `"`, `*`, `-`, `NEAR`, or a bare column name can't throw an FTS5 syntax error or be silently reinterpreted as an operator. Verified with a test that searches for exactly those characters.
- **The migration test's fixed table-name assertion was updated, not the migration**, once `schema-v2.db` came out with FTS5's shadow tables (`endings_fts_data`, `_idx`, `_docsize`, `_config`) alongside `endings_fts` itself — real SQLite bookkeeping for the virtual table, not part of this app's own schema. The test now filters `endings_fts_*` before comparing, keeping the assertion meaningful (catches a genuinely missing/extra app table) without hard-coding FTS5's internal implementation detail.
- **History's search box replaces the filtered list rather than narrowing it.** Typing a query switches the screen from "filtered session list" to "matching endings across all of history" — the two never combine (e.g. "search within the last 30 days" isn't wired up). No ticket asked for scoped search, and search-then-filter is a second interaction model layered on the first for a feature this app's design direction (§10, quiet/restrained) doesn't obviously need yet.
- **Found and fixed in passing: the pre-existing migration test mutated the committed fixture files on every test run.** `it.each(...)('upgrades the committed v%i fixture cleanly to current', ...)` opened `fixturePath(version)` directly with `node:sqlite`'s `DatabaseSync` and ran real `migrate()` DDL against it — since a fixture file is a real file on disk, not a copy, this permanently upgraded `schema-v1.db` to the current schema version the first time the suite ran after migration 0002 landed (caught because `git status` showed `schema-v1.db` modified with no corresponding source change). Fixed by copying the fixture to a temp file (`fs.mkdtempSync`) before migrating and deleting the temp dir after — the committed fixture is now only ever opened read-only by this test. Restored `schema-v1.db` to its pre-bug bytes before committing.

## Review mode (ticket 13)

- **The 3 meta-stems (§5.4) are seeded as real `stems` rows** (`origin = 'meta'`, `active = 0`, `category = NULL`), not kept out of the table as the ticket-02/03 entries above implied. `sessions.stem_id` is `NOT NULL REFERENCES stems(id)` (spec §4.2) and §6.5.2 requires the meta-stem to be presented "as a normal timed session" — i.e. a real `sessions` row like any other — so a meta-stem session needs a real `stems.id` to point at; there is no schema affordance for a session without one, and inventing a fake/sentinel id would have broken the FK's intent (even though SQLite isn't enforcing it at runtime here — no `PRAGMA foreign_keys = ON` anywhere in this codebase — a dangling reference would still corrupt every join that assumes `stem_id` resolves: history, `getRecentStemUsage`, the debug dump). `active = 0` keeps them out of `listActiveStems` (so `selectStem`/weighted rotation can never draw one) by the exact same mechanism archived stems already use; `origin = 'meta'` is the new discriminator so `listAllStems` (feeds the stem library) and `listStemTexts` (feeds the "not a verbatim duplicate" check on adding a stem) can exclude them explicitly, since those two are the only reads where a meta-stem leaking through would be visibly wrong — everywhere else (history, `getRecentStemUsage`) a meta-stem-derived row is either correctly visible (a review session is a real session, it belongs in history) or harmlessly inert (its `stem_id` never matches any `listActiveStems` candidate). `Repository.listMetaStems()` is the one new read this requires.
- **`useWritingSession.start()` gained an optional `configOverrides: { targetEndings?, timerSeconds? }`** on `StemForSession`, rather than a parallel `startReview()` method. Review's meta-stem session (§6.5.2: "a normal timed session… with a longer default timer… and `origin = 'review'`") is otherwise identical to any other session — same creation, autosave, finalize, and cold-start/backgrounding rules (ADR-0001) — so overriding the two config values that differ (`targetEndings: 1`, `timerSeconds: settings.review_timer_seconds`) keeps one code path instead of forking it.
- **`src/session/reviewPeriod.ts` is a pure module** (`computeReviewPeriod`, `isWeeklyReviewDue`, the `REVIEW_PERIOD_PRESETS`/`DEFAULT_REVIEW_PERIOD_DAYS` constants for Q4), matching the existing pattern (`stemSelection.ts`, `uncensoredEdit.ts`, `stemLibraryFilter.ts`) of keeping anything with a date/time edge case (period boundaries, the 7-day "due" threshold) outside the component tree and directly unit-testable.
- **The "offered once a week" prompt (§6.5) is a single unemphasised line on the `/review` screen itself** ("It has been a week or more since your last review."), computed once at that screen's mount, not a home-screen badge/indicator. A first attempt put the due-check on the home screen via `useFocusEffect`, but that broke `index.test.tsx`'s existing render-only smoke test (`useFocusEffect` requires a navigation context the bare `render(<HomeScreen />)` doesn't provide) and was inconsistent with this codebase's established rule that the home screen only touches `@/db` inside interaction handlers, never at render/focus time (see the ticket-06 DECISIONS entry above). Moving the check onto `/review` — which already calls `getRepository()` in lazy `useState` initializers for its other data — fixed both problems at once and reads more consistently with §13.4/§13.6 anyway: a quiet sentence on the screen where you'd act on it, not a badge competing for attention on the home screen.
- **`reviews.session_ids` stores the ids of the sessions re-read (the _reviewed_ sessions), not the meta-stem session created during review.** The meta-stem session is a new, ordinary session in its own right (`sessions`/`endings` rows, `origin='review'`) and is discoverable through the normal `stem_id`/`origin` columns like any other — `reviews.reflection_text` denormalizes its one ending's text onto the review row (mirroring `stem_text_snapshot`'s reasoning, §4.4: a review's own record of what was written shouldn't shift if something upstream changed), so nothing is lost by not also listing it in `session_ids`.
- **Meta-stem choice is uniform-random among the 3, not weighted or sequential.** Spec §5.4/§6.5 say nothing about ordering or weighting meta-stems (unlike §6.2's explicit weighted-draw requirement for regular stems), so `Math.random()` over `listMetaStems()` is the simplest thing that satisfies "present one meta-stem" without inventing a rotation policy no ticket asked for.

## Export (ticket 14)

- **A hand-rolled, dependency-free ZIP writer (`src/export/zip.ts`) rather than a library.** No zip package was already installed (checked `node_modules` first), and every candidate (`jszip`, `adm-zip`, `fflate`) is either large or brings compression machinery the CSV set doesn't need — this app's whole corpus is plain text, and STORE (uncompressed) entries are still tiny. The writer is ~100 lines: a CRC32 table, local file headers, a central directory, and the end-of-central-directory record — the complete subset of the ZIP spec a STORE-only archive needs. It deliberately only writes, never reads, a zip (nothing in this app unzips anything; import restores from the JSON bundle per spec §8). `node:zlib.crc32` was available in the Node test environment but not used, since it doesn't exist under Hermes on-device — the same CRC32 table runs identically in both.
- **The raw SQLite export uses `SQLiteDatabase.serializeSync()`, not a file copy.** `serializeSync()` returns the exact on-disk bytes after `PRAGMA integrity_check` and `VACUUM` run via the normal `execSync` path — this is simpler than copying the underlying database file (whose location/name is an internal detail of `expo-sqlite`) and guarantees the exported bytes are a real, directly-openable SQLite file, matching "the highest-fidelity option" language in spec §8.1.
- **The JSON bundle's `settings` field is an array of raw `{key, value, updated_at}` rows, not the single decoded object spec §8.2's example shows (`"settings": {...}`).** The ticket's own acceptance criterion is "lossless... every column appears in the JSON and CSV exports" — collapsing to decoded key/value pairs would drop each setting's own `updated_at` and require a lossy re-encode on import. Read the spec's `{...}` as illustrative shorthand, not a literal schema, and followed the ticket's more specific lossless requirement plus consistency with the other four tables (all arrays of raw rows).
- **Only `stems`, `sessions`, `endings`, `reviews`, `settings` are in the JSON bundle and CSV set** — `notification_schedule` and `schema_meta` are excluded, matching spec §8.2's JSON example and §8.3's explicit four-file CSV list exactly. Both are operational bookkeeping (scheduling state, migration history), not part of the user's written corpus that "stays open to analysis" (§8's stated purpose); `Repository.dumpAllTables()` (used by the debug screen) still includes them for that unrelated purpose.
- **Export screen (`/export`) does two things per tap: pick a format, get the share sheet** — Home → Export (tap 1) → a format card (tap 2, which itself triggers `Sharing.shareAsync`) satisfies "reachable in two taps... offered via the system share sheet" (§8) without an intermediate confirmation step, since nothing is written or sent until the second tap.
- **The CSV README is a single large template string in `csvBundle.ts`**, not a separate file/generator. It's static prose describing a schema that changes only via a numbered migration (rare, deliberate) — a docstring generated from the DDL would be more "correct" but is speculative machinery for a document that's supposed to read like documentation, not be derived data itself.
- **The round-trip test (`src/export/__tests__/roundTrip.test.ts`) writes a deliberately CSV-hostile corpus** (ending text containing quotes, a comma, and an embedded newline) and asserts the JSON bundle is byte-identical before/after an export→wipe→import(replace)→export cycle, modulo `exported_at` — this is §8's own explicit test ("assert byte-identical modulo the exported_at field"), and it's the one place ticket 14 and ticket 15's logic (`applyImport`) necessarily meet, so `importBundle.ts` was built as part of this ticket rather than deferred whole to 15, exactly as ticket 15 itself expects ("Round-trip fidelity... covered by ticket 14's test").
- **`applyImport`'s `replace` mode deletes tables in reverse declaration order (`endings` → `sessions` → `stems`, etc.)** before re-inserting in forward order. `node:sqlite` (used in tests) enforces foreign keys by default; `expo-sqlite` in production does not (no `PRAGMA foreign_keys = ON` anywhere in this app, per the ticket-13 entry above) — deleting/inserting in dependency order is correct and required under the former, and a harmless no-op ordering choice under the latter, so one code path is correct for both rather than branching on which engine is live.

## Settings + delete-all-data (ticket 16)

- **`Repository.setSetting` is an `INSERT ... ON CONFLICT(key) DO UPDATE`, one call per key**, rather than a bulk `setSettings(partial)`. The settings screen already knows exactly which key changed (each control's `onChange` fires independently) — a bulk setter would just re-encode the same information the caller already has, and per-key writes keep `updated_at` accurate per row instead of bumping every key's timestamp on any single change.
- **`Repository.deleteAllData()` is a `DELETE FROM` on every user-data table (children before parents, same ordering `applyImport`'s replace mode already established in ticket 14) inside one transaction, followed by `seedIfEmpty()`** — not a `closeSync`/`deleteDatabaseSync`/reopen cycle. The module-level `db`/`repository` singletons in `src/db/database.ts` are held by reference in multiple places (hooks, screens); dropping and reopening the file would invalidate those references without a way to notify every holder. A `DELETE FROM` achieves the same observable outcome ("drops and recreates the database" per spec §9 — nothing survives, the schema itself is untouched because nothing but rows changed) without that hazard. `schema_meta` is deliberately excluded: it's migration bookkeeping (§13.8), not user data, and wiping it would make the app think a fresh install needs to migrate from version 0 on next open even though the schema itself never changed.
- **The settings screen calls `rescheduleNotifications()` after saving the notification window or `sessions_per_day`**, wiring up the seam ticket 10 built and flagged as deferred ("Settings change" and "timezone change" ... have no call site yet because no settings screen exists"). Every other setting (`endings_per_session`, `timer_seconds`, `uncensored_mode`, `stem_terminator`, `app_lock_enabled`, `weekly_review_prompt`, `theme`) has no effect on the notification schedule, so those setters skip the reschedule call — it would be a correct no-op either way (`generateFireTimes` doesn't read those keys) but calling it unconditionally on every keystroke-adjacent change would be needless native-module traffic.
- **The notification window is edited as a single start/end pair (`TextInput`, `HH:MM`), not a repeating add/remove list**, even though `Settings.windows` and spec §7 allow "one or more". The seed default is exactly one window and no ticket (09, 10, 16) asks for a multi-window editor; `generateFireTimes` already supports an array, so a future ticket can extend the UI without a schema or logic change. `src/session/settingsValidation.ts#isValidHHMM` validates the format before the value is written.
- **"Delete all data" gets two sequential `Alert.alert` confirmations, not one**, going beyond the single-confirmation pattern used elsewhere (stem soft-delete, import replace). This is spec §9's explicit "hard confirmation" for "the one legitimate hard wipe" in a codebase whose default posture is soft-delete-only (§13.5) — asymmetric friction for the one action in the app with no undo of any kind, including from export. The copy suggests exporting first, per the ticket.
- **`cancelAllPendingNotifications()` (new export in `scheduler.ts`, wrapping `Notifications.cancelAllScheduledNotificationsAsync()`) is called before `repo.deleteAllData()`** on the delete-all-data path — an unconditional stop, distinct from `rescheduleNotifications()`'s diff-and-reconcile behaviour, since after a wipe there is no `notification_schedule` row left to reconcile against and every pending OS notification would otherwise reference stems that no longer exist.
- **`src/app/about-method.tsx` (ticket 17's own checklist item, "reachable later") was built now, in this ticket, rather than left as a dead link.** The settings screen's "About the method" entry point only makes sense once something is actually behind it; shipping a `Link` to a route that doesn't exist yet would be a broken link in this ticket's own commit. Its copy (crediting Branden by name, pointing to _The Six Pillars of Self-Esteem_ and _The Art of Living Consciously_, no verbatim text) satisfies §5.1's "SHOULD do the same at more length" and is what ticket 17 would otherwise have had to write from scratch — ticket 17 just links to it from onboarding instead of building it again.

## Onboarding (ticket 17)

- **"Shown once" is a raw `settings` row (`onboarding_completed`), read/written via two new `Repository` methods (`isOnboardingComplete`/`setOnboardingComplete`), deliberately kept out of the typed `Settings` interface/`DEFAULT_SETTINGS`.** It isn't one of spec §7's user-facing tunables — it's app-internal "has this run" state — so it shouldn't appear on the object every settings-reading call site destructures. `getSettings()` was tightened to exclude it at the query level (`WHERE key != 'onboarding_completed'`) once a test caught it leaking through the existing `SELECT key, value FROM settings` spread.
- **The onboarding gate lives in `src/app/_layout.tsx` (`useOnboardingGate`, a `useEffect` keyed on `useSegments()`), not in `index.tsx`.** `index.test.tsx` is a bare `render(<HomeScreen />)` with no navigation context and no expectation that mounting it touches `@/db`/`expo-sqlite` — the same constraint DECISIONS.md already documents for ticket 06 (home's `getRepository()` call is deferred to the button handler) and ticket 13 (the review-due check moved off the home screen for the same reason). The root layout is never rendered by that test, so checking `Repository.isOnboardingComplete()` there and `router.replace('/onboarding')`-ing when it's false and the current route isn't already `/onboarding` is the one place in the app that can do this check unconditionally without touching an existing test.
- **All four screens are one route (`/onboarding`) with a local `step` state (0–3), not four separate routes.** The flow is strictly linear with a single "Skip" affordance that exits the whole thing at any step — a `step` counter expresses that directly; four routes would need to pass "have I already skipped" state through router params for no benefit, since nothing else in the app ever deep-links into the middle of onboarding.
- **Notification permission is requested by a real button tap ("Allow reminders"), never automatically on mount.** Spec §6.1 step 3 and §6.4 both require an honest, explained ask; `requestNotificationPermission()` (ticket 10's seam) is called only from that tap. Declining ("Not now") sets local state and advances to the prefs step — no retry, no re-prompt, matching "must not nag" (§6.1) exactly, since onboarding itself only ever runs once per `isOnboardingComplete()`.
- **The prefs step's window fields are only shown/persisted if notifications were just allowed.** Setting a notification window when the user has no notification permission would be dead configuration with no observable effect (`rescheduleNotifications()` is a no-op without permission, per ticket 10) — asking for it anyway would be exactly the kind of unused-input friction the app's quiet/restrained direction (§10) argues against. Declining still gets `sessions_per_day`/`endings_per_session`/`timer_seconds` (used regardless of notifications), just not the window.
- **`finish()` writes `sessions_per_day`/`endings_per_session`/`timer_seconds`/`windows` via the same `Repository.setSetting` ticket 16 added**, not a new bulk onboarding-specific writer — onboarding's prefs step is just "the first time these particular settings get set," so it reuses the exact persistence path the settings screen uses for the same keys later.
- **Declining notifications never calls `rescheduleNotifications()`**; only a granted permission does, on `finish()`. Calling it after a decline would be a no-op (it checks `hasNotificationPermission()` internally and returns early) but skipping the call entirely is one fewer async call on the path most likely to be taken by someone who just said no.

## App lock (ticket 18)

- **Lock state is a pure function, `src/session/appLock.ts#nextLockState(enabled, wasLocked, event)`**, matching the existing pattern (`reviewPeriod.ts`, `uncensoredEdit.ts`, `stemSelection.ts`) of keeping anything with a time/state edge case outside the component tree. It's a plain state machine over three events (`cold_start` always locks when enabled; `foreground` locks only if the background gap was ≥60s, per §9/ticket 18, and never *un*locks an already-locked app early; `authenticated` always unlocks) — no `AppState`, no `expo-local-authentication`, no wall clock, so it's fully unit-tested without a device.
- **Graceful fallback lives in `useAppLock.ts`, not in the pure module**: `enabled` is only ever passed through as `true` if `hasHardwareAsync()` _and_ `isEnrolledAsync()` both resolve true. A device with app-lock turned on but no biometric/passcode enrolled behaves identically to the setting being off — the app never locks, per the ticket's explicit "never lock the user out of their data." This is checked once per mount (cold start), not re-checked on every foreground, since enrollment changing mid-session is rare enough that a fresh cold-start check on next launch is sufficient and avoids a native call on every foreground transition.
- **`useAppLock` tracks background duration in a plain `useRef`, updated from a single `AppState` listener registered once (empty effect deps)**, with the enrollment result also stored in a ref (`canLock`) rather than state — the listener closure must read the _current_ enrollment/lock values, not the ones captured when the effect first ran, and a ref sidesteps re-subscribing the listener on every render (the same `AppState.addEventListener` pattern `useNotifications.ts`'s `useNotificationScheduler` already uses, extended here with a second piece of tracked state).
- **The lock screen replaces `<Stack>` entirely in `_layout.tsx`** (`lock.locked ? <LockScreen .../> : <Stack ... />`), rather than rendering as an overlay on top of it. An overlay would still mount every screen underneath — including `/write`, whose stem text is exactly what §9's lock exists to hide from anyone who picks up the phone before authenticating.
- **`src/app/lock-screen.tsx` is deliberately content-free** — no stem text, no session state, no hint of what's inside — the same lock-screen-privacy reasoning spec §6.4 already applies to notification copy, applied here to the in-app lock screen itself.
- **`app.json` gained the `expo-local-authentication` config plugin entry (no custom options)**, matching the existing pattern for `expo-notifications`/`expo-splash-screen` (ticket 10's DECISIONS entry). Not a new dependency — `expo-local-authentication` was already installed (spec §3's own dependency table) — this only adds the native config step (`NSFaceIDUsageDescription` on iOS, `USE_BIOMETRIC`/`USE_FINGERPRINT` permissions on Android) without which FaceID would silently fail to prompt on iOS.
- **No settings-screen change**: `app_lock_enabled`'s `ChipToggle` already existed on `/settings` from ticket 16 (it's one of §7's stated keys, seeded `false` by default) — ticket 18 only had to make the setting actually do something.

## Import (ticket 15)

- **`/import`'s "Replace" option gets an `Alert.alert` confirmation before running; "Merge" does not.** Same asymmetry the ticket-08 entry above draws between soft-delete and archive: replace is a destructive, one-way (from inside the app) wipe of everything currently in the database, while merge only ever adds rows that don't already exist by id — nothing existing is touched or removed, so it doesn't need the same friction.
- **Import only restores the JSON bundle, not the SQLite-copy or CSV-zip export formats**, matching the ticket's own scope ("Imports a previously exported JSON bundle") and spec §8's own import requirement, which names only the JSON bundle. Someone with just the SQLite copy can already open it directly with any SQLite tool; someone with the CSV zip has the same option via a CSV importer if they need it — round-tripping either of those back into this app's schema was never asked for.
- **`pickAndImportBundle` calls `Repository.rebuildEndingsFts()` unconditionally after every import (merge or replace), not just when new `endings` rows were actually inserted.** `applyImport` returns only aggregate `{inserted, skipped}` counts, not which tables changed, and a rebuild on an unchanged index is cheap and idempotent (`INSERT INTO endings_fts(endings_fts) VALUES ('rebuild')` — the same call `repository.search.test.ts` already exercises for correctness) — simpler than threading "did endings change" out of `applyImport` for a conditional skip that only matters on a merge importing zero rows.

## Accessibility & design pass (ticket 19)

- **`Colors` (theme.ts) gained an `error` key, per-theme** (`#B3261E` light, `#FF6659` dark) rather than one hex reused on both. The pre-existing hard-coded `color: '#B3261E'` (stem-edit and settings validation errors) measured 3.2:1 against black — below WCAG AA's 4.5:1 — despite passing (6.5:1) against white; §10's "dark mode is not an afterthought" makes that a real bug, not a rounding issue. Both new values were checked with the same relative-luminance formula the rest of this audit used, against `background` in their respective theme.
- **`write.tsx`'s dimmed "past endings" list dropped its `opacity: 0.5` overlay on `textSecondary`.** `textSecondary` alone already clears 4.5:1 in both themes (5.9:1 light / 10.1:1 dark) and was the intended "de-emphasised but present" treatment; stacking 50% opacity on top of it measured 2.1:1 (light) / 3.0:1 (dark) — well under AA. The color is the dimming; opacity on top of an already-secondary color was redundant and broke contrast, not a second usable channel.
- **New `MinTouchTarget = 44` constant in theme.ts**, applied to every `Pressable`/`Link` whose visible content (small text, a `±` glyph) was smaller than a 44pt tap target: onboarding's copy of the sessions/endings/timer stepper (was 40×40, `settings.tsx`'s own copy was already 44), the home screen's nav `Link`s, the exit/"Done"/"Delete" text-only controls on write/session-detail/stem-edit, and the header Import/Add/Edit links on the stem library. Apple HIG and Material Design both cite 44pt/48dp as the accessible minimum; none of these were unreachable, just below spec for anyone with reduced dexterity or a shaky hand at 2am, which is this app's stated primary use case (§10).
- **New shared `src/components/filter-chip.tsx` (`FilterChip`)**, replacing six near-identical `chip`/`FilterRow` `StyleSheet` definitions duplicated verbatim across `history.tsx`, `review.tsx`, `settings.tsx`, `stem-edit.tsx`, `stem-import.tsx`, and `stems.tsx` (all the same `paddingVertical: Spacing.one, paddingHorizontal: Spacing.two, borderRadius: Spacing.three` selectable-chip pattern). Consolidating them was both the ticket's explicit ask ("if there's a shared theme/tokens module, consolidate through it rather than per-screen constants") and the fix for the same sub-44pt touch-target gap those chips all shared — one component, one place the tap-target and selected-state accessibility logic can be correct, instead of six copies that could each drift.
- **The writing screen's top "Close" affordance is now `idle`-phase only**; during `active` and `done` it deferred entirely to the "Done"/"Close" controls those phases already render. Previously "Close" was visible in every phase, so an active session had two simultaneous ways to leave the screen (the top "Close", a bare `router.back()` that does not finalize the session, and the bottom "Done", which calls `finishNow()` and saves) — spec §10's "no navigation chrome at all beyond a single exit affordance" is a hard per-screen-state constraint, not just a count of buttons at any one time. Functionality is unchanged: leaving without tapping anything (backgrounding, interruption) still resolves via the existing timeout/absence-grace finalisation in `sessionMachine.ts` (untouched by this ticket), so no path that used to save a half-typed ending stops doing so.
- **No motion/animation code exists anywhere in `src/app` or `src/components`**, checked explicitly (`Animated`, `withSpring`, `Easing`) — confirmed compliant with "motion is limited to fades and the timer's progress; nothing bounces" by absence rather than by adding fade transitions no ticket asked for. The timer itself is already a non-numeric `accessibilityRole="progressbar"` (a 0–100 `accessibilityValue`, no seconds-remaining numeral rendered anywhere) on both `write.tsx` and `review.tsx`'s meta-stem session — confirmed pre-existing and unchanged.
- **Deferred, not fixed: the per-screen `TextInput` font sizes** (`stem-edit.tsx`'s 18px input, `stem-import.tsx`/`onboarding.tsx`/`settings.tsx`'s 16px inputs) stay as local `StyleSheet` values rather than being pulled into `theme.ts` alongside `ThemedText`'s scale. `TextInput` is a different component from `ThemedText` and needs its own style object regardless; the five numeric duplicates are a single literal each, not enough duplication to justify a new shared token over the existing `Fonts`/`Colors`/`Spacing`/`MinTouchTarget` set. All of them do inherit Dynamic Type scaling from the RN default (`allowFontScaling: true`, never overridden anywhere in this codebase).

## Post-implementation review (all tickets)

- **`Repository.updateStem` overwrites `stems.text`/`category` in place; this is sanctioned by spec §4.4, not an append-only breach.** The append-only rule ("never overwrite a row to represent a state change") protects the journaling record; spec §4.4 explicitly says "Users will edit their own stems" and answers editability with `sessions.stem_text_snapshot` — the DDL comment reads "denormalised on purpose: stems can be edited". An untouched, never-keypressed field mirrors session-level timeout exactly: no `endings` row is created at all (`finalizeSession` only touches rows that already exist; `expireActiveEnding` does the same). Six new reducer tests cover this (`src/session/__tests__/sessionMachine.test.ts`). `useWritingSession.ts` wires it as a second, independent 1Hz countdown (`stemRemainingSeconds`) alongside the existing session countdown, reset every time `activeOrdinal` changes; the session timer's own interval and `computeReturnAction`/ADR-0001 resume logic are untouched, so the session timer still wins if it expires first. `stem_timer_seconds` is not persisted per-session (no `sessions` column, no migration) — it is re-read from current settings both on `start()` and on cold-start resume, the same way `uncensored_mode`'s _display_ already isn't re-derived from a stale snapshot for anything not in `SessionRow`.
  - **Enter-to-submit required a small correctness fix beyond wiring `onSubmitEditing`.** The input stays `multiline` (unlike a first-pass instinct to drop it) because a non-multiline RN `TextInput` scrolls horizontally instead of wrapping, which would be a regression for a full sentence; with `multiline`, the return key is delivered as a trailing `"\n"` via `onChangeText`, not via `onSubmitEditing` (kept anyway for platforms/configurations where it does fire). Naively calling `changeActiveText(text-without-\n)` immediately followed by `submitActive()` would submit stale text, because `submitActive` reads `stateRef.current`, which is only synced from React state in a separate `useEffect` that hasn't run yet at that point in the same synchronous handler. Fixed by giving `submitActive` an optional `overrideText` parameter that write.tsx passes directly; internally it runs the override through the same `applyEdit` gate as every other keystroke before submitting, so uncensored mode's backspace-within-word/no-cut restrictions apply identically regardless of entry path (Enter vs. the Next button) — this was verified by hand-tracing `applyEdit`'s existing test cases against the override path, no separate test needed since no new pure logic was added, only a new caller of the same gate. Submitting on Enter or the button both now ignore an empty field (`text.trim() === ''`); timeout and per-stem expiry are unaffected and still save an empty field per §6.3.8's existing rule, since they go through `finalize`/`expireStem`, a different path entirely.
  - **Pressure visuals are additive UI only, no new dependency.** The per-stem countdown reuses the same thin-bar `ThemedView` pattern already used for the session timer (still neutral-colored, not red — §6.3.7's "no red" is about that indicator, not the button). The Save/Next button's background is an `Animated.Value` driven by `1 - pressureFraction` (per-stem fraction when the per-stem timer is on, else the session fraction) interpolated between two new fixed colors, `PressureColors.calm`/`PressureColors.urgent` (`src/constants/theme.ts`) — fixed rather than theme-dependent because the gradient needs one guaranteed-readable label color across its whole range, and computing that separately per theme wasn't worth the complexity for a background that's already a deliberate departure from the theme palette. White label text measures a minimum 5.13:1 contrast across the full gradient (worst point, not just the endpoints — the RGB lerp passes through olive/brown, never a bright yellow, so there's no midtone contrast dip to trap). No scoring/shaming copy anywhere near it, per §13.4.
- **The Save/Next button's label became the countdown itself, and the completion view shows total session duration** (2026-09-11 user feedback, follow-up to the pressure gradient above; ticket `07-timer-button.md`). The button shows `m:ss` of whichever timer already drives its color (`pressureFraction`'s existing per-stem-else-session selection) instead of static "Next" text — the color and the number are now the same signal at two resolutions, coarse (gradient) and precise (digits), rather than a countdown living only in the thin progress bars above. Falls back to the old static label if neither timer has a value, which shouldn't occur while `phase === 'active'` but costs nothing to guard. Because the visible label no longer reads as an action verb, the button gained an explicit `accessibilityLabel="Save this ending"` so VoiceOver/TalkBack users still hear a save affordance rather than a bare timer readout. Two small pure functions, `formatMMSS` and `sessionDurationLabel` (`src/session/sessionMachine.ts`, sibling to the module's other pure reducer/query helpers), do the formatting; `sessionDurationLabel` is computed at read time from the session's already-persisted `startedAt`/`endedAt` (§13.7 — duration is never itself stored) and is deliberately terse ("6 endings · 4:32") with no praise/evaluation language near it (§13.4). Both functions have unit tests covering rounding, zero-padding, singular/plural, and negative/non-finite clamping to `0:00`.

  - `ThemedText` gained an `eyebrow` type (12px/16, sans, 600 weight, uppercase via `letterSpacing`, `textSecondary` by default) — the one gap the audit named: nothing previously distinguished "a label above a group" from small secondary body text, and the new `SectionHeader` needs it.
